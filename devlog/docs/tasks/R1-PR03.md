# R1-PR03: contention, retry and response-loss evidence

Status: implemented locally, 2026-10-23. Validated using the
actual `submit_purchase` service and runtime credentials. Preserve PR01/02 evidence
as historical runs, with new evidence for changed source bytes.

## Required work

- Drive two simultaneous debits of 80 against customer 100 using separate real
  connections/processes. Exactly one acceptance and one retained insufficient-funds
  rejection; final customer 20/merchant 80, one purchase journal and correct fold.
- Exercise concurrent same-key/same-payload, new-key/same-operation, and differing
  payloads. Force the uniqueness wait and prove the following statement sees the
  committed winner. No duplicate effect, stale snapshot or orphan claim.
- Drive lock timeout and cancellation while another transaction holds a relevant
  lock. Distinguish retryable unretained failure from a saved business rejection;
  prove connection/lock cleanup and subsequent same-identity success or replay.
- Add bounded whole-transaction retries (at most three attempts, jitter) only for
  deadlock/serialization SQLSTATEs. Preserve IDs; never retry just the failing SQL
  statement. Do not retry arbitrary integrity faults or infer rollback on ambiguous
  connection loss. Verify the caller owns the connection lifecycle.
- Lose the reply after the service has committed. A reconnect with either original
  key or a new key for the original operation returns the original journal/result.
  Explicitly distinguish known committed/reply lost from COMMIT outcome unknown.
- Demonstrate actual rollback on interruption before commit and correct recovery
  after unknown commit outcome, using process/connection fault injection rather
  than a fake exception that assumes the answer.

## Quality and scope

Use events, barriers and PostgreSQL observed lock relations to establish ordering;
fixed sleeps and timeouts cannot establish success. Freeze input cases beforehand,
retain independent journal fold and literal ownership expectations, and ensure
mutation counterexamples fail for the intended reason. Do not make this a throughput
benchmark or introduce pooling, HTTP, workers, providers, reversals or deployment.

Present any new material design choices together in one 3–5-item packet. Existing
four defaults remain accepted. Implementation/verification/personal ownership are
separate facts; progress does not assert that the user has independently mastered it.

## Delivery

The production change is a bounded retry wrapper around the existing whole admission
transaction. [ADR 0004](../../../docs/adr/0004-contention-and-recovery.md) records error selection,
attempt count, backoff and caller-owned connection recovery. Tests use actual runtime
connections, PostgreSQL lock dependencies, SQLSTATE fault injection, process SIGKILL
and observed COMMIT protocol frames; no production failpoint was added.

[PR03 evidence](../../evidence/R1-PR03/2026-10-23/README.md) records final regression,
source hashes, build checks and the test-proxy cleanup problem found and fixed during
verification. PR01/02 records remain historical. This completes this three-part R1
core slice; HTTP/token verification, persistent local database setup and broader
source-package deliverables require their own task contract. R2 reversal/freeze/
rebuild and later provider work are still deferred.
