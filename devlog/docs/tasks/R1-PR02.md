# R1-PR02: Python purchase admission

Status: implemented locally on 2026-10-23. Follow the accepted defaults,
[ADR 0002](../../../docs/adr/0002-r1-foundation.md) and [working contract](../working/R1-CONTRACT.md).
Keep work local and retain one small decision packet for material user choices.

## Outcome

Implement a Python service function accepting validated purchase input, authenticated
workspace/client/actor context and scoped request key. It must return a stored result
after one explicit PostgreSQL transaction commits. No HTTP framework, provider or
reversal is needed. Use real runtime credentials in integration tests.

## Transaction obligations

1. Acquire the transaction-scoped shared workspace maintenance barrier before
   reading mode. Check NORMAL, with a stable documented lock-key mapping. R2's
   exclusive freeze uses the same key; no write may precede admission to the barrier.
2. Verify scoped authentication, account existence, enabled state, currency, classes
   and customer/merchant ownership. Decide error precedence and exact stored result
   shapes in a reviewable contract before coding; do not infer authorization from UUIDs.
3. Reserve the scoped request key and workspace business ID. Compare canonical bytes,
   not just hashes. Replays return original accepted/rejected results; changed payloads
   conflict. A new request key for the same operation must bind to the same result.
   Catch only named expected identity conflicts using a recoverable transaction path.
4. Lock affected account balances in stable account-ID order at READ COMMITTED,
   recheck available balance, and apply checked integer deltas. Retain an insufficient-
   funds rejection without any journal or balance mutation; new funding does not
   rewrite that historical result.
5. For acceptance, atomically write the declared journal and exact entries, increment
   projection versions, and finalize operation/request records with matching results.
   No accepted purchase may commit without its intended journal and projection changes.
6. Commit before returning success. Keep external I/O outside the transaction and
   release locks/connection on errors. Do not broadly convert SQL faults into business
   rejection. Opening funds remain explicit setup journals, not a public purchase path.

## Required evidence

- Real service calls produce the frozen 100→20 customer / 0→80 M1 outcome; the
  independent fold and original request assertion both pass.
- Rejection persists and stays rejected after new funding; byte-identical retries and
  a new request key for the same business ID return the original result without effects.
- Changed bytes under either identity conflict; scope separation and authorization
  failures cannot transfer funds or disclose another scope's retained response.
- Inject failure between journal, projection and result writes: all effects roll back.
- Demonstrate transaction barrier ordering and freeze-mode rejection with deterministic
  connection coordination. The full drain/export mechanism remains R2.
- Keep PR01 protections green; add meaningful cases for result/journal binding. PR03
  adds the complete simultaneous debit/retry/lost-reply suite; do not claim it in advance.

Record code, tests and personal ownership separately. No tracker, push, deployment,
GitHub PR, reversal, worker or AI layer is included.
