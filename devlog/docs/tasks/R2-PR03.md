## Concrete interface

`submit_reversal(conn, principal, ReversalCommand, request_key)` uses the same
Principal, idle autocommit connection and result/error family as purchase. Command:
typed workspace_id, operation_id, original_operation_id; reason exact nonempty UTF-8
1–256 bytes without NUL. Canonical prefix `ledgerops.reversal:v1\n`; fixed JSON field
order workspace_id, operation_id, original_operation_id, reason, default ASCII
escaping and compact separators. Request route `reversal:v1`. Purchase v1 unchanged.

Only the original merchant actor may reverse an already committed accepted PURCHASE
with matching canonical request, complete journal/result and exact original entries.
Unknown, foreign, rejected, OPENING or reversal originals are ineligible. Return
generic authorization error without claims; corrupt original invariants roll back.
No caller-chosen amount, accounts or currency. No partial refund, provider operation,
customer-triggered unilateral refund, approval system or HTTP adapter.

201 exact fields: operation_id, original_operation_id, admission="accepted",
journal_id, amount_minor string, currency="PLN", effect="purchase_reversed",
contract_version integer1. Persisted422 uses existing immutable error envelope:
INSUFFICIENT_AVAILABLE / LIMIT_EXCEEDED / ALREADY_REVERSED (message "Purchase already
reversed"). Check prior success before availability. Identity409 remains unretained.
Original purchase stays accepted; do not edit any old entry/header/result.

## Transaction and schema

One finite purchase/reversal orchestrator owns settings/shared barrier/mode/auth,
request-key claim then operation-ID claim, common replay and result finalization.
Keep existing `_submit_purchase_once` retry-test boundary via a thin wrapper;
purchase and reversal share bounded whole-transaction 40P01/40001 retry. No generic
plugin framework or copied transaction. Reuse sorted balance lock and transfer SQL.
Preclaim authorization uses immutable original reads, not new original row locks.
New reversal locks its accepted original FOR UPDATE after its own claims, then locks
balance rows in ascending UUID order. Replays validate stored ownership before
disclosing conflicts/results and do not re-decide historical outcomes or take new
original/balance locks. Scope includes workspace/client/route/key; cross-kind
business-ID collisions authorize the stored operation before disclosing a conflict.

Migration005 extends kinds/routes, adds immutable reversal_attempt and success-only
purchase_reversal_effect. Attempt references are nonunique by original; success
relation PK (workspace, original) and UNIQUE(workspace, reversal) allow only one
success. All attempts survive, including failed ones. No ON CONFLICT swallowing on
success insertion. Unexpected23505 propagates and rolls back; it is not a result.

DB deferred guards bind every committed reversal to one accepted PURCHASE attempt;
accepted REVERSAL requires one success relation and two-line journal with the same
declared total as original. Rejected reversal has neither effect nor journal.
Foreign keys enforce scope/type/binding, guards preserve immutability and terminal
structure. Python and independent B establish exact canonical intent/accounts/amount;
DB constraints alone do not prove ownership or journal/projection equality.
Only app has INSERT on new relations; reader/maintenance SELECT only. No new login.
