# R3-PR04 进程恢复与故障矩阵

基线 `ff9a70e`。沿用 R3 已采纳合同，补齐实际 worker 进程和端到端恢复，保留001–007字节。
本片不增加生产 HTTP，不修改 lab、教程、参考原件或其他项目。证据随一个本地提交保存。

## 运行进程

`python -m ledgerops.worker` 使用专用 worker 凭据，一个进程最多一个数据库连接；
批量、轮询、claim 租期、单次网络调用均有边界。只扫描配置的支付商 namespace，
每次 claim 仍重新核对工作区和身份。正常运行不将外部调用放进金融事务。
`--once` 处理一批；`--max-calls` 用于有限运行，达到次数后退出。

配置与数据分开：恢复模式默认开启、派发默认关闭。必须明确设置恢复模式为 false 且
派发为 true，才允许启动付款 worker；恢复出的 NORMAL 数据库本身无权打开它。
启动检查实际数据库身份的 worker 权限和非高权限属性、迁移能力；不能拿 owner 连接冒充运行身份。
日志仅输出事件、公开的业务关联和分类，不输出 DSN、口令、HMAC、原始支付指令或 SQL 参数。

SIGINT/SIGTERM 停止领取新工作，完成当前有界调用并关闭自己的连接。配置错误、不满足角色/
迁移能力、受信数据不变量破坏明确失败退出；不能反复扫描坏队头而声称健康运行。
暂时的数据库错误采用有界轮询重连。未知结果继续按原身份查证，不因退出或次数达到上限释放 hold。
实际模拟支付商适配器仍只使用 loopback；不将它冒充真实银行集成。

## 验收矩阵

1. provider after-commit 屏障已观测后 SIGKILL worker，独立 SQLite 效果保留；
   PG 仍是80/62/18。重启按同 key 观察，最终18/0/18、清算38，一个 journal/消费事件/效果。
2. claim 已提交但请求尚未交给 provider 时 kill；恢复不能按“测试知道没发”释放，
   截止后须取得永久关单，80/0/80；延迟同 key PUT 不得执行。
3. 成功被滞后查询遮蔽、ACCEPTED 跨进程重启、显式 FAILED、有界未决、旧202均按原契约。
   不靠 sleep 推定先后，用实际 gate/请求/SQL状态；超时只作为失败保护。
4. idle/在途 SIGTERM 退出、restore 配置零出站、namespace 隔离，检查进程和连接清理。
5. 活动 hold 下修复 booked/reserved 漂移后，经真实 provider 成功结算，独立核对健康。
6. 语义变异：未知时释放、重试换 key、忽略旧终局矛盾、按 event ID 忽略不同字节、
   漏减 reserved、绕过冻结、hold/intent 分事务、journal/消费分事务。
   必须命中目标业务断言；语法错误、fixture失败、超时不算。数据库 guard 拦住的缺陷
   单独记清，不把它说成独立核对器发现。

同时运行全量回归、Ruff、实际安装包检查。实际结果写入 evidence，不在合同里预先填“通过”。
R3 的恢复前提仍是本地准入/身份/hold 历史完整；旧备份缺业务历史属于 R5。
没有权威证据时可以一直未决，不保证任意时序收敛，不证明电源故障、真实银行或生产容量。
