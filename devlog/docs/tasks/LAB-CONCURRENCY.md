**scope**

这两个面板调用现有购买与维护接口，用实验专用阻塞连接控制推进。等待关系来自独立观察连接查询 pg_stat_activity 和 pg_blocking_pids；教学文字不是锁观测。

**observation_note**

箭头方向是等待者 → 阻塞者，来自这一份数据库观测。query 是 PostgreSQL 当时报告的语句；若会话处于 idle in transaction，它显示的是最近一条语句，并不表示那条语句仍在执行。观测有时间戳，历史记录不代表此刻仍在等待。

**trace_note**

每个参与者的 SQL 记录只包含它实际发出的客户端命令及调用位置。执行中的语句还没有返回，不会预填成功、耗时或 COMMIT。触发器内部语句不在这份客户端追踪内。

**cleanup_note**

刷新、重置和清理会取消本场景未完成的工作，回滚仍打开的实验事务并关闭连接。已经提交的业务不会因为清理连接而撤销。重新开始场景使用新工作区，不把取消和冲正混为一谈。

**watchdog_note**

场景有300秒的总等待保护，过期会取消并清理。为留出阅读时间，实验连接还会额外执行延长数据库超时的SQL，具体配置值可在真实追踪中查看；生产入口原有5秒锁超时、10秒语句超时保持原样。超时不用于判断顺序；正常推进以真实阻塞关系和线程实际结束为依据。

### 两笔80，竞争客户余额100

两笔不同业务共用客户余额。实验阻塞者先持有余额行锁，让购买A、购买B进入可观察的等待；你放行以后，它们才能依据最新余额完成判定。

先看真实PID、wait_event和blocking_pids，再看阻塞SQL。PostgreSQL可能让B等待A持有的元组锁，而不直接等待最初的阻塞者；按实际报告理解这条链，不强求一张预设图。

**实验阻塞者不是业务规则**

阻塞连接只在临时数据库里持有客户余额行的FOR UPDATE锁。它给你时间看见两个业务请求卡在哪。真正扣款的仍是submit_purchase；实验没有另写一套购买算法。

为什么：如果只连续点两次购买，第一笔可能早已结束，看不出两个事务竞争同一行时发生了什么。受控阻塞把这个短暂阶段停在可检查的位置。

保证者：本地实验调度器控制阻塞事务；PostgreSQL执行真实行锁；购买入口保持原样。

代码：lab/concurrency.py；src/ledgerops/db/admission.py · submit_purchase / _lock_balances

**等待结束后，重新基于最新行判断**

余额行按账户UUID排序加锁。READ COMMITTED下，等待行锁的购买取得锁后使用该行的最新值，再检查booked − reserved。余额100不能支撑两笔80；一个成功后，另一个只能保存余额不足的422。

为什么：先读到100再各自扣80，不能构成安全的并发判定。判断与写入必须发生在同一个持锁事务中。

保证者：Python规定账户排序和余额判断；PostgreSQL串行化同一余额行的修改，CHECK另行阻止透支。

代码：src/ledgerops/db/admission.py · _lock_balances / _transfer_rejection / _post_transfer；src/ledgerops/db/sql/001_foundation.sql

**最终状态仍要独立核对**

201和422说明入口给出了两个判定；还要看只新增一笔购买分录，客户20、商户80，并运行独立核对A和B。借贷平衡或没有透支，仍不足以证明钱给了正确商户。

为什么：线程成功退出不等于业务正确。最终余额、分录和保存的原始请求应当互相吻合。

保证者：独立核对器从原始分录重算余额，并独立解析保存的请求；它不复用生产记账步骤。

代码：src/ledgerops/verification.py · verify_snapshot / _check_projections / _check_intent

### 购买还没结束，冻结必须等待

购买先持有工作区共享屏障，再被实验余额锁挡住。随后发起冻结，观察维护连接等待购买的共享屏障。放行购买后，冻结才能完成。

需要看到两条真实依赖：购买等待实验阻塞者的余额锁，冻结等待购买持有的advisory锁。不要把页面里写着“准备冻结”当作数据库已经冻结。

**先拿屏障，再读工作区模式**

业务事务在身份认领和余额写入之前拿共享事务级advisory lock，然后读取mode。维护流程拿同一键的排他锁。共享与排他互斥，因此冻结必须等已进入的购买结束。

为什么：只把mode字段改成FROZEN，可能漏掉已经进入的写事务；等待共享锁释放，才能把这些协作写事务排空。

保证者：Python要求受控入口遵守同一屏障协议；PostgreSQL执行锁互斥，并在事务结束时释放事务级锁。

代码：src/ledgerops/db/admission.py · _open_admission；src/ledgerops/db/maintenance.py · _transaction / freeze_workspace

**购买提交以后，冻结才会看到稳定状态**

解除实验余额锁后，购买继续写分录、投影和保存结果。共享屏障随事务结束释放，维护才能取得排他屏障并把工作区置为FROZEN。随后新购买先拿共享屏障，再读到FROZEN，返回503，且不保存新的业务身份或资金效果。

为什么：冻结前的在途业务可以正常完成；冻结后的新业务必须遵守新的模式。这两个时点由数据库锁建立关系，而不是页面计时。

保证者：现有购买和冻结接口建立事务边界；独立观察连接验证等待关系；最终快照核对确认保存状态。

代码：src/ledgerops/db/admission.py · _submit_once / _open_admission；src/ledgerops/db/maintenance.py · freeze_workspace

**数据库冻结的保证有范围**

屏障约束遵守协议的购买、冲正和维护入口，不自动拦截数据库所有者的任意SQL。FROZEN也不证明外部付款已停止，更不会撤回已经发往第三方的请求。本项目当前没有接外部支付渠道。

为什么：数据库状态和外部系统状态是两种证据。将来增加worker或渠道回写，需要单独设计它们怎样遵守屏障。

保证者：本实验只验证已实现的数据库入口与屏障；没有外部付款停止保证。

代码：src/ledgerops/db/admission.py · _open_admission；src/ledgerops/db/maintenance.py · _transaction

**面试深挖：冻结与排空为什么不是一回事**

冻结是工作区模式；排空是等待已进入的协作写事务结束。当前协议先用排他屏障排空，再修改模式，避免在途事务在维护窗口里继续写入。

**面试深挖：为什么冻结后的新购买是503**

503表示当前模式暂时不可受理，不是已经保存的余额不足422。它不应留下新的身份认领或分录；恢复后仍应保留原业务身份重新提交，而不是凭网络或模式错误随便换ID。
