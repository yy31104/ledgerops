# R1-PR01: executable contract foundation

Status: implemented and verified locally, 2026-10-23. The user authorized this slice
and accepted [decision packet 1](../DECISION-PACKET-R1.md). This is a local task ID,
not a published GitHub pull request.

## Outcome

Create a reviewable schema/role/fixture foundation on real PostgreSQL before the
successful posting flow. [ADR 0002](../adr/0002-r1-foundation.md) records the implemented
Python/direct-SQL trust boundary and changes from the historical initialization ADR.

## Scope

- Specify typed workspace, actor, account and operation UUIDs; request-key scope;
  canonical payload bytes and exact equality/replay rules.
- Define synthetic PLN money as integer minor units, amount range
  `1..9_000_000_000_000_000`, field-specific zero rules and checked aggregate bounds.
  Reject bool, float, exponent notation, signs and noncanonical integer strings.
- Add reproducible migrations for workspace, immutable account identity, projection,
  operation, request-result, journal and entry. Opening balances use journals.
- Set up distinct migration and least-privilege runtime roles, a documented privilege
  matrix and disposable real PostgreSQL test environment; record exact versions.
- Implement deferred complete/balanced-journal checks plus historical immutability.
  Select and document protection against INSERT under an already committed journal.
- Freeze input fixtures before exercising the implementation: clearing/customer
  funding 100; customer purchases 80 from M1; distinct M2 available as wrong-owner case.
- Add a small independent entry fold and literal business expectations, with no
  production money/posting helper used to compute expected outcomes.

No production purchase admission is required in this slice. Fixture construction
must explicitly identify any privileged setup; it cannot stand in for runtime tests.

## Acceptance

1. A clean environment can migrate and create the declared roles reproducibly.
   Record version/configuration, commands, fixture digest and actual test outcomes.
2. Real commit attempts with zero entries, one entry, or unequal debit/credit sums
   fail. A complete valid fixture commits; no committed draft bypass exists.
3. Run the revised `T-AUTHDB-01` using real runtime credentials: allowed operations
   work; historical UPDATE/DELETE/TRUNCATE, DDL, privilege escalation, trigger/seal
   bypass and cross-workspace relations are refused by their declared controls.
   Do not assert blanket INSERT denial after granting selected direct SQL access.
4. Commit a valid journal, then attempt a balanced pair of INSERTs involving two
   new accounts in another transaction. The attempt fails and history is unchanged.
   Prove runtime cannot reopen or forge the protection; include concurrent attempts
   against the selected mechanism when they could race creation/sealing.
5. Money/schema boundary cases reject invalid values and overflow on the real DB.
   Scope-bearing foreign keys and immutable account owner/class/normal side hold.
6. The independent fold obtains clearing 100, customer 20, M1 80 and M2 0 from the
   opening plus purchase fixture. Include zero-activity accounts explicitly.
7. Deliberately omit the customer projection update: fold comparison fails.
   Credit M2 in both journal and projection: fold may agree, but the frozen command's
   ownership assertion fails. Use isolated, explicit defect injection and demonstrate
   that each failure is caused by the intended defect, not a broken setup.
8. `make check`, meaningful unit/integration tests and build pass. PostgreSQL tests
   cannot become green through mocks, unconditional skips or an unavailable server.
