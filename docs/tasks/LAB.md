### 第1步：先开户：这 100 究竟是谁的钱？

建立客户、两家商户和清算账户，用已有合成夹具记入第一笔开户分录。此时才真正出现余额。

观察重点：清算资产增加 100，客户负债增加 100。资产和负债同时增加，账仍然平。

你看到的“客户余额”，从平台的角度看，是平台欠客户多少钱。把观察视角固定在平台，借贷方向就有了依据。

**先别把借方理解成扣钱**

借方（Debit / D）和贷方（Credit / C）是两侧记账符号。资产账户借方增加，负债账户贷方增加。开户写 D 清算 100、C 客户 100，所以两边余额都增加 100。这不是把客户的钱扣给平台。

保证者：Python 夹具指定账户与方向；数据库检查分录结构、借贷合计及余额行约束。

代码：lab/session.py · LabSession._opening（适配已有工作区的账户创建）；tests/integration/helpers.py · post_fixture（合成开户分录）；src/ledgerops/db/sql/001_foundation.sql

**一份事实，两种表示**

journal / journal_entry 保存不可修改的记账事实；account_balance 保存当前余额投影，方便快速扣款检查。投影应能从全部分录重新算出，但数据库 CHECK 本身不能证明这两份数据始终一致。后面的核对 A 专门检查这个关系。

保证者：数据库保护已提交分录；独立核对器比较分录重算值与余额投影。

代码：src/ledgerops/verification.py · _check_journals / _check_projections

**这里的开户为什么标为合成夹具？**

R1/R2 没有接银行充值或实际清算。本实验复用测试夹具生成开户分录，独立核对器能验证它的结构，不能把它证明成真实入金。报告会披露 OPENING 的业务意图尚未核实。

**最小货币单位为什么用整数？**

本账本的 PLN 金额按分 / grosz 存储，所以 100 表示 1.00 PLN。请求金额按精确整数解析，不用二进制浮点数表示货币。页面也将金额作为字符串发送和展示，避免 JavaScript 大整数精度损失。

**代码阅读重点**

先找 account、journal、journal_entry 和 account_balance 四张表，再看金额和 booked 的约束。表里的每一行对应下面证据区中的实际记录。

页面代码入口：schema, transfer, verify

**面试深挖：项目在做什么**

这是一个 Python + PostgreSQL 的平台账本。R1 处理购买、幂等和并发扣款；R2 增加独立核对、冻结重建和全额冲正。它没有对接真实银行，也没有实现支付渠道。

**面试深挖：分录平衡能证明一切吗**

不能。给错误商户记一借一贷，合计仍然平；只改余额而不改分录，也可能满足行内 CHECK。所以需要数据库结构约束、业务代码和独立核对三层不同的证据。

### 第2步：购买成功：把一笔业务装进一个事务

客户向商户 M1 购买 80。观察业务结果、两行分录和两个余额如何一起提交。

观察重点：D 客户 80、C 商户 80。平台欠客户的减少，欠商户的增加；清算资产没有再次流动。

这笔购买改变的是平台内部“欠谁的钱”。借记客户负债会减少客户余额，贷记商户负债会增加商户余额。

**事务保护完整的一笔业务**

业务身份与请求结果、分录表头和两行分录、两个账户投影在一个显式数据库事务里完成。COMMIT 成功才整体生效；中途异常会 ROLLBACK。不会留下“客户扣了、商户没加”的半笔业务。

保证者：Python 控制事务边界和写入顺序；PostgreSQL 提供原子提交，并在提交时执行延迟约束。

代码：src/ledgerops/db/admission.py · _submit_once / _post_new_purchase / _post_transfer

**锁住后才判断可用余额**

事务先通过工作区共享屏障，再依次认领请求键与业务 ID，最后按账户 UUID 排序锁余额行。READ COMMITTED 下，等待行锁结束后读到该行的当前值，再判断 booked − reserved 是否足够。本课按顺序执行；可以在真实 SQL 中找到锁语句，也可展开并发面板观察实际竞争。并发单步演示不是容量压测。

保证者：Python 规定加锁顺序与业务判断；数据库行锁串行化对同一余额的修改，余额 CHECK 拦截透支。

代码：src/ledgerops/db/admission.py · _open_admission / _submit_once / _lock_balances / _transfer_rejection

**为什么不能先 SELECT 余额，再 UPDATE？**

如果两个事务都先读到 100，然后各扣 80，单靠旧读值判断会出错。当前实现把“等待行锁、读最新行、判断、写入”放在同一个事务中。约束是最后防线；数据库仍不会自动证明收款商户正确。

**业务 ID 和请求键，到底差在哪？**

业务 ID 标识“哪一笔业务”，请求键标识“这个调用方在这条路由上的哪次逻辑请求”。请求键还绑定规范化内容。原身份、原内容的重试读回原结果；换内容复用原键是 409 冲突。要发起另一笔购买，应使用新的业务 ID 和请求键。自由实验区能直接比较这两种操作。

**代码阅读重点**

把 _submit_once 当作目录读：工作区入口 → 请求键 → 业务 ID → 重放或新业务。再打开 _post_transfer 看分录和投影的具体 SQL。

页面代码入口：purchase, balance_lock, transfer, replay

**面试深挖：为什么选显式 SQL**

锁、冲突等待和事务顺序是项目的核心，手写 SQL 便于审查这些顺序。Python 负责业务流程，数据库约束保护可表达的结构规则；没有宣称数据库单独保证所有业务正确性。

**面试深挖：为什么固定账户排序**

多个事务若按不同顺序锁同一组账户，可能形成 A 等 B、B 等 A。统一按 UUID 排序能消除这类余额行的循环等待；它不意味着任意未来新增的加锁路径都自动安全。

### 第3步：余额不足：拒绝也是要保存的结果

用新的业务身份再次购买 80。客户可用余额不足，保存 422 拒绝结果，但不产生购买分录。

观察重点：业务表和请求表多了一条拒绝，分录及余额不变。数据库事务提交不等于业务一定成功。

“业务失败”和“事务失败”不同。余额不足是确定的业务结论，应当正常提交这份拒绝记录。

**永久保留一次业务的判定**

同一业务之后即使有了钱，原身份重试仍返回当时保存的拒绝。否则客户端丢失响应后重试，可能把原本已拒绝的业务变成成功，语义就不稳定了。重新尝试一次业务，需要新的业务 ID。

保证者：Python 保存 422 与拒绝码；数据库唯一关系保护业务身份；重放代码检查身份和原始内容。

代码：src/ledgerops/db/admission.py · _rejection / _finish_operation / _finish_request / _retained_result

**断线不等于没有入账**

服务端可能已 COMMIT，但响应尚未送达客户端。此时客户端无法单靠网络错误确定成败，应保留原业务 ID、原请求键和原内容重新提交，读取已保存结果。页面的“原购买身份重放”会真正调用这条路径，不会凭空再扣一次。

保证者：持久化业务结果与分录在同一事务；Python 重放分支返回保存结果。

代码：src/ledgerops/db/admission.py · _replay_by_request_key / _replay_by_operation

**哪些错误允许服务端自动重试？**

当前生产入口只对 SQLSTATE 40P01（死锁）和 40001（序列化失败）做有上限的整笔事务重试，并保留原身份。超时、取消和断线不被泛化成自动重试。执行过程若没有采集到重试，就只展示本次实际执行，不画一条假重试链。

**201、422、409、503 各表示什么？**

201 是保存的成功结果；422 是保存的业务拒绝；409 表示身份与内容冲突；503 可表示工作区冻结等暂时不可受理。前两种保存结果会在原身份重试时稳定返回，不能把所有非 2xx 都当作“换个新 ID 重发”。

**代码阅读重点**

对照实际返回结果的 error.code，以及 operation / request_result 中的 http_status。重放前后比较操作数、分录数和余额。

页面代码入口：replay, purchase, balance_lock

**面试深挖：幂等保证的精确边界**

项目让同一业务身份最多形成一次已保存的记账效果，并重放原结果。它不承诺网络只投递一次，也不使用“整个分布式世界 exactly-once”这种超出实现范围的表述。

**面试深挖：为什么不自动重试全部数据库异常**

业务拒绝无需重试；身份冲突需要调用方修正；未知提交结果需要原身份恢复。只有明确允许的事务失败码，才由入口限次重跑整笔事务。

### 第4步：全额冲正：保留历史，写一笔相反的账

由原购买的商户主体发起全额冲正。原分录保留，再写 D 商户、C 客户的一笔新分录。

观察重点：购买没有被删除。两张 journal 一正一反，业务与原购买之间留下明确关系。

冲正不是把数据库改回旧样子，而是追加一个有独立身份、能够追溯到原购买的业务。

**先锁原购买，再锁余额**

冲正先锁住原购买那一行，再按 UUID 排序锁相关余额。同一原购买的冲正因此逐个判定。购买不会去锁别人的业务记录；重放不新增余额锁；在这些现有路径下，不会因它们之间的反向依赖构成循环等待。

保证者：Python 规定原购买锁和余额锁顺序；PostgreSQL 执行 FOR UPDATE 和唯一约束。

代码：src/ledgerops/db/admission.py · _original_purchase / _post_new_reversal / _lock_balances

**授权与业务条件分开**

只有原商户主体能发起冲正。原购买不存在、未成功，或调用者不是原商户，统一 404，避免暴露资源存在性。确认资源可访问后，再判断是否已冲正、商户可用余额是否足够。

保证者：Python 依据可信 Principal 校验商户归属；数据库不会从浏览器输入自动推断登录身份。

代码：src/ledgerops/db/admission.py · Principal / _original_purchase / _post_new_reversal

**Principal 和数据库角色不是一回事**

Principal 表示业务调用者是谁，真实服务必须由可信认证边界构造；数据库角色限制一条连接能写哪些表。本页固定课堂身份，没有生产登录。购买用 app 角色，核对用 reader，维护用 maintenance；开户建账户、重置建工作区及故障注入使用临时库所有者。角色是此实验连接的逻辑别名，不是浏览器登录角色。

**为什么不是客户拿购买 ID 就能退款？**

如果任何客户都能凭 ID 扣商户余额，接口就承诺了客户单方面退款。当前 R2 选择原商户发起的全额冲正，没有实现退款审批、部分退款或真实支付渠道退款。

**代码阅读重点**

比较购买和冲正：它们共用事务入口、身份认领、重放与转账步骤。只有资源授权、原购买锁、反向分录和成功关系不同。

页面代码入口：reversal, purchase, transfer, schema

**面试深挖：为什么不更新原分录**

追加相反分录能保存当时发生的事实和后来纠正它的事实，便于导出和追溯。原始错误或原购买仍在历史里，因此冲正不等于抹除所有核对告警。

**面试深挖：当前边界**

只支持成功购买的全额冲正。若原客户账户已停用，新冲正会返回 404，且不保存成 422 业务拒绝；这条已披露的边界不能讲成任意退款都留拒绝记录。

### 第5步：重复冲正：同一个重试，和另一笔业务

换一个新的冲正业务 ID 再冲正原购买。得到 422 ALREADY_REVERSED，并保留这次失败尝试。

观察重点：新业务重复冲正被拒；重放成功那次身份仍返回201，重放拒绝那次身份则返回422。重放均不新增分录。

“成功最多一次”和“失败可以保留很多次”应该用不同的关系表达。否则一次失败就可能封死后来的合法重试。

**成功关系的键，选原购买 ID**

purchase_reversal_effect 的主键是 (workspace_id, original_operation_id)，所以同一工作区内的一笔原购买最多关联一次成功冲正。reversal_attempt 的主键是 (workspace_id, operation_id)，所以失败尝试不会占用那一个成功名额。每个唯一性结论都限定在工作区内。

保证者：数据库通过两张表的不同主键执行唯一性；Python 在原购买锁内判断并保存结果。

代码：src/ledgerops/db/sql/005_full_reversal.sql；src/ledgerops/db/admission.py · _post_new_reversal

**余额不足后，补款仍可再冲正**

若商户余额不足，第一次冲正会保存拒绝。之后补款，用新的冲正业务 ID 才能进行新的余额判断并成功；用原 ID 只会重放原拒绝。失败记录不得挡住新的成功，这也是 R2 的核心验收场景。标准十二步不额外演示补款流程。

保证者：Python 保存独立的失败尝试；成功关系只在接受冲正时写入；集成测试覆盖失败后新身份成功。

代码：src/ledgerops/db/admission.py · _post_new_reversal / _retained_reversal_result；tests/integration/

**页面上的“原冲正身份重放”重放哪一次？**

本按钮重放最近一次提交的冲正，包括保存的拒绝。标准故事第5步提交了新的重复冲正，所以此后点击重放会再次得到那次422，而不是第4步成功的201。要观察成功重放，可在第4步后进入自由实验再点重放；这时最近一次还是成功冲正。真实请求键和业务ID显示在返回结果旁。

**为什么用 422，不用 409？**

“原购买已经成功冲正”是稳定的业务结论，用 422 ALREADY_REVERSED 保存。409 留给“复用同一身份却换了请求内容”。不能只看 HTTP 状态，就把两种错误的恢复动作混为一谈。

**为什么不捕获所有唯一键冲突后当作已冲正？**

正常路径已经先锁原购买再查成功关系。如果仍出现未预期的唯一键异常，可能说明锁约定被绕过或有其他缺陷；把它一概吞成业务拒绝会掩盖错误。

**代码阅读重点**

证据区同时查看原成功冲正、当前失败冲正，以及 reversal_attempt / purchase_reversal_effect。数量关系比单看一句“没重复扣款”更有说服力。

页面代码入口：reversal, replay, schema

**面试深挖：解释唯一键选择**

尝试表按尝试业务 ID 去重，效果表按原购买 ID 限定一次成功。这样保存失败历史和限制成功次数两个需求互不干扰。

**面试深挖：业务身份与新尝试**

重试恢复一个已有判定；新尝试请求重新判定。是否允许新尝试，应由业务条件决定，不能靠随意生成新 ID 来绕过唯一规则。

### 第6步：制造漂移：约束全部通过，余额仍可能错

只在临时实验库中，用所有者权限把客户余额投影增加 20。分录完全不变，制造一份可修复的漂移。

观察重点：余额变了，journal 没变。一个非负余额仍可能是错误余额。

这一步是反例：数据库里每行看起来合法，不代表行与行、表与表之间表达了同一笔业务。

**CHECK 能检查什么**

行内 CHECK 可以要求 booked ≥ reserved ≥ 0，生成列可以要求 booked 始终由累计借贷计算。但如果有人把累计 credits 多加 20，生成的 booked 也会多 20，行内条件仍可能成立。

保证者：数据库执行可表达的行内规则；跨表投影一致性由独立核对器发现。

代码：src/ledgerops/db/sql/001_foundation.sql；src/ledgerops/verification.py · _check_projections

**这不是普通用户可以使用的业务能力**

本按钮是实验专用的故障注入，使用临时库所有者连接。它不经过购买入口，也不能据此声称普通商户可以修改任意余额。真实风险还包括具有写权限的应用代码写错，因此独立核对不能由权限控制完全替代。

保证者：实验适配器限制在本次临时数据库；生产核心的 app / reader / maintenance 角色按各自权限运行。

代码：lab/session.py · LabSession._drift；src/ledgerops/db/sql/001_foundation.sql

**为什么不能把“借贷平衡”当作最终正确性证明？**

一是本例：只改余额投影，借贷分录仍平衡；二是记错商户：分录和余额都同时记给 M2，一借一贷也平衡。前者核对 A 能发现，后者需要核对 B 对照原始请求。

**为什么已提交分录不能再追加一借一贷？**

journal 表头预先声明行数和总额，提交时延迟检查实际分录是否完全符合。原表头又不能改，因此事后追加一对平衡行，也会因不符合原声明而被拒绝；只检查借贷总和相等是不够的。

**代码阅读重点**

把约束能保证的性质逐项写清：数值范围、借贷平衡、不可追加、唯一身份。不要把“余额等于分录重算”默认为普通 CHECK 已经保证。

页面代码入口：schema, verify, transfer

**面试深挖：这个反例的价值**

我用故障注入证明了数据库结构正确和业务正确是不同性质，再用独立算法核对投影。验证是主动尝试构造错误，而不只是跑成功路径。

**面试深挖：信任边界**

数据库所有者能绕过许多普通角色限制，实验使用它制造故障。项目没有宣称能抵御被完全控制的数据库所有者，也没有把本地演示包装成生产安全证明。

### 第7步：导出并核对：两个问题，分别回答

用只读角色导出一个一致快照，再让不连接数据库的独立核对器读文件。查看 A 失败、B 通过的具体差异。

核对 A：余额是否等于分录重算？核对 B：分录是否符合当时保存的业务请求？它们不能互相替代。

核对器必须自己重算，而不是再次调用当初可能记错账的生产函数。否则两边共享同一个错误，也能“相互印证”。

**A 看投影，B 看业务意图**

A 从全部分录按账户重算累计借贷，包括没有交易的账户，再与余额逐项比较。B 独立解析 operation 中记账前保存的原始 payload，核对客户、商户、方向和金额。只把账记平不能代替这两项检查。

保证者：仅依赖 Python 标准库的独立核对器实现；不导入生产记账步骤。

代码：src/ledgerops/verification.py · _check_projections / _check_intent / _check_reversals / verify_snapshot

**所有表必须来自同一时刻**

若逐表各开一个查询事务，期间正好有一笔购买提交，导出的业务、分录和余额可能拼成数据库从未存在过的状态。导出使用一个 REPEATABLE READ 只读事务，让全部表共享一致快照。离线核对随后只读完成的导出文件。

保证者：PostgreSQL 提供事务快照；导出器设置读取边界；离线核对器不持有数据库连接。

代码：src/ledgerops/export.py · capture_snapshot / export_workspace / load_export；src/ledgerops/verification.py · verify_snapshot

**B 通过，就能证明原始业务一定真实吗？**

不能。如果原始请求本身一开始就存错，B 只能证明分录与这份已存请求相符。测试里的手工冻结指令清单额外检查请求没有记错。实际运行不要求先有手工清单，所以普通本地业务也能核对和重建。

**历史拒绝为什么不重新算一次余额？**

今天的余额不是拒绝发生时的余额。核对器检查拒绝没有误产生分录，而不拿当前余额倒推当时是否应该拒绝。合成 OPENING 的真实意图也没有被 B 证明，报告会披露未核实的类型。

**核对报告为什么会过期？**

报告描述的是某个导出快照。后续写入或修复不会改变那份旧文件，但会让它不再代表当前状态。页面将过期报告明确标记；预览和旧报告都不能作为当前余额直接回写。

**代码阅读重点**

逐个读 structure_ok、projection_ok、request_intent_ok 和 reservation_supported。healthy 只由结构、A、B 三项组合；reservation_supported 另行参与重建准入，不参与 healthy。健康报告不证明真实世界付款完成。

页面代码入口：verify, export

**面试深挖：怎么发现记错商户**

如果分录和余额都错记给同一商户，A 可能仍通过。B 从原始请求独立恢复预期收款人，会报 WRONG_OWNER。两种故障分别检验了不同性质。

**面试深挖：为什么要保留导出版本**

迁移增加后旧证据仍需要可核对。导出格式版本与支持的 schema 列表绑定，新核对器保留旧格式处理，不能简单把旧包当作不合法。

### 第8步：冻结之前，先等在途写事务结束

维护连接取得排他工作区屏障，等待已经进入的写事务结束，再把模式设为 FROZEN。

观察重点：冻结是一道写入闸门。余额和原始分录尚未修复，FROZEN 也不会自动变回 NORMAL。

先改一个状态字段还不够。若已经在跑的购买事务继续提交，维护看到的就不是稳定的账。

**共享屏障与排他屏障**

业务写事务先取得事务级共享 advisory lock，再读工作区模式；维护先取同一个屏障的排他锁。排他锁会等待已经持有共享锁的写事务结束。后来进入的业务等到锁后重新读模式，看到 FROZEN 就不能新记账。

保证者：Python 约定全部受控写路径经过屏障；PostgreSQL 执行共享 / 排他锁与事务结束自动释放。

代码：src/ledgerops/db/admission.py · _open_admission；src/ledgerops/db/maintenance.py · _transaction / freeze_workspace

**冻结的是数据库写入边界**

FROZEN 不代表外部付款已经停止，也不取消已发出的网络请求。当前 R2 没有外部支付渠道，不能用数据库冻结推断第三方状态。未来 worker、外部结果回写等写路径也必须明确遵守屏障协议。

保证者：本阶段只验证已实现的购买、冲正与维护路径；没有外部付款停止保证。

代码：src/ledgerops/db/maintenance.py · freeze_workspace；src/ledgerops/db/admission.py · _open_admission

**为什么先拿锁再读模式？**

如果先读 NORMAL，再等待屏障，等待期间维护可能已经冻结。拿到锁后仍沿用旧模式，就会越过闸门。正确顺序是取得共享屏障后读取模式，这一点能从实际 SQL 顺序检查。

**advisory lock 能阻止所有 SQL 吗？**

不能。它是约定式锁，只约束主动使用同一个锁键的代码；数据库所有者手写不遵守协议的 SQL 仍可绕过。权限、代码入口和独立核对分别保护不同边界，不能把 advisory lock 讲成全库自动停写。

**代码阅读重点**

先看共享和排他锁使用的同一个工作区键，再看 mode 在锁之后读取 / 写入。执行过程页展示本次真实 SQL；要看真实共享屏障等待，请展开另设的并发单步面板。

页面代码入口：freeze, purchase, resume

**面试深挖：冻结与停机的区别**

冻结是受控写入口遵守的数据库维护模式，排空在途事务后获得稳定维护窗口。它不等于停止整个进程，更不等于停止第三方支付。

**面试深挖：为什么要显式恢复**

修复提交只是完成数据变更。保留 FROZEN 让维护者还能再次核对，再用独立动作恢复写入，避免“修复函数返回就自动营业”的隐式状态跳转。

### 第9步：先看差异：预览是证据，不是待激活余额

在冻结状态下导出并生成差异报告。预览指出哪些账户的投影与分录重算不符，尚未修改余额。

观察重点：预览前后实际余额相同。接下来的应用重建会在事务里重新计算，不把预览文件当作资金来源。

预览让人知道准备修什么；现场重算保证真正写入时依据的是数据库中的分录。两者承担不同责任。

**为什么不建候选余额代次**

当前 R2 在冻结并持有排他屏障的事务中现场重算，没有候选表和激活生命周期。这样仍有先看差异、全成或全败、修复可追溯三项保证，且不需要额外维护候选过期状态。

保证者：Python 维护流程在排他屏障内读取来源；应用函数自行重算目标，不信任预览数值。

代码：src/ledgerops/db/maintenance.py · preview_rebuild / _targets / apply_rebuild

**准入不要求余额本来正确**

重建要求结构正确、业务意图 B 通过，并且没有非零预留。它不要求 A 先通过，因为修复 A 发现的投影漂移正是重建的目的。B 不通过可能说明来源业务错了，不能靠重算投影把它“洗成健康”。

保证者：维护代码检查独立核对报告；非零预留会阻止应用重建。

代码：src/ledgerops/db/maintenance.py · _require_source / apply_rebuild；src/ledgerops/verification.py · VerificationReport.rebuild_eligible

**预留金额为什么阻止重建？**

reserved 表示资金已被占用，不能仅靠普通已记账分录恢复其完整生命周期。R2 没有实现预留的独立重建，所以遇到非零预留宁可拒绝应用，而不是把它悄悄归零。

**预览中的导出 ID 有什么作用？**

preview_export_id 是调用者提交并写入修复日志的审计引用，让记录能标识调用者声称看过哪份预览。它不证明操作者真的读过文件，也不证明文件真实性。真正写入仍现场重算，不从该文件复制余额。

**代码阅读重点**

对照 preview.changes 的 before / after 与当前 balance。再看 apply_rebuild 如何重新构造 snapshot 和 SQL targets，而不是读取预览中的 after 值。

页面代码入口：repair, verify, export

**面试深挖：为什么简化候选方案仍安全**

当前工作量和维护窗口允许在一个排他事务中现场计算，所以无需为预先物化的候选引入额外生命周期。如果将来数据规模要求离线计算，需要重新设计一致性与激活契约。

**面试深挖：为什么记错人不能只重建余额**

错误商户已经写进分录来源。按这些分录重算只会继续把钱给错误商户。重建只修“投影偏离来源”，不修“来源表达了错误业务”。

### 第10步：现场重建：余额、修复日志、代次一起提交

在排他屏障与单个事务里，从分录重新计算并写入余额，保存改前 / 改后记录，将 projection epoch 增加 1。

观察重点：客户投影被修正，旧分录不动，修复日志新增，工作区仍为 FROZEN。

修复不是一条没有说明的 UPDATE。必须让后来的人看见：依据什么、改了哪些账户、前后值各是多少。

**SQL 算一次，独立 Python 再查一次**

应用重建用 SQL 从分录现场聚合目标余额，写入后在同一事务内再让独立核对器检查。若两套算法不一致或任何步骤失败，余额、修复明细和 epoch 都回滚。已有变异测试验证过：把旧预览值塞进写入路径会被独立检查发现。

保证者：Python 运行来源检查与写后核对；PostgreSQL 保证全部写入原子提交；独立核对器不复用 SQL 目标算法。

代码：src/ledgerops/db/maintenance.py · _targets / _write_projection / apply_rebuild；src/ledgerops/verification.py · verify_snapshot

**epoch 和 version 不是一个计数器**

projection_epoch 标识整个工作区经历了哪次投影重建；账户 version 标识某个余额行的更新版本。一次正常购买会更新相关账户 version，但不会因此产生一次全库重建 epoch。它们都不是余额，也不能代替业务 ID。

保证者：维护事务更新 workspace epoch 和账户版本，并写入不可改的修复记录。

代码：src/ledgerops/db/maintenance.py · _write_projection / apply_rebuild；src/ledgerops/db/sql/003_projection_maintenance.sql

**修复日志为什么也要防追加？**

只禁止修改和删除还不够。若能在原修复记录下继续追加明细，就能改写它看起来修过哪些账户。修复记录同样声明账户数并在提交时核对实际明细，提交后不能随意加行。

**应用成功后为什么不自动恢复？**

重建提交后仍冻结，维护者可以核对修复记录和最新数据。恢复是下一步显式动作，并且会重新检查当前状态，而不是沿用上一步“应该已成功”的假设。

**代码阅读重点**

把 apply_rebuild 的事务边界画在余额 UPDATE、repair / repair_row INSERT、epoch UPDATE 和写后核对之外。任何一步出错都不应留下半份修复。

页面代码入口：repair, verify, schema

**面试深挖：独立核对比重复断言更强在哪**

生产写入算法和验证算法分别实现，能发现一方的错误。若测试只是调用生产 helper 计算 expected，再与 helper 结果比较，就可能共同保留同一个缺陷。

**面试深挖：为什么不要直接用预览余额**

预览用于人看差异和事后引用。应用时在锁内重新读取分录并计算，减少过期来源问题；再用独立核对确认本次写入，而不把文件里的值当作真值。

### 第11步：恢复营业：用当前状态重新过闸门

恢复时重新检查结构和余额核对 A。通过后保存恢复报告，显式把工作区切回 NORMAL。

观察重点：恢复准入与重建准入不同。B 告警或非零预留要保留，但不能把冻结变成无法解冻的单向门。

维护流程负责让投影恢复可信；它不应该要求所有历史业务问题都先消失，才允许系统重新运行。

**两道门，条件不同**

apply_rebuild 要求结构正确、B 通过、预留为零；resume_workspace 只要求结构正确和 A 通过。B 的问题和非零预留仍进入报告与恢复记录，但不阻止恢复。不要把两个条件复用成同一个布尔值。

保证者：Python 分别检查两类准入；数据库恢复记录约束也要求保存的结构 / A 检查为 true。

代码：src/ledgerops/db/maintenance.py · _require_source / resume_workspace；src/ledgerops/db/sql/004_resume_review.sql

**为什么 B 失败仍可能需要恢复**

如果历史购买记错人，原分录不可改，冲正后原始错误也仍在。若恢复必须 B 通过，但冲正又只允许 NORMAL，便形成“先纠正才能恢复、先恢复才能纠正”的死循环。恢复保留告警，不把它假装解决。

保证者：独立核对持续报告业务意图问题；恢复记录保存报告；业务纠正走独立、可审计的路径。

代码：src/ledgerops/db/maintenance.py · resume_workspace；src/ledgerops/verification.py · _check_intent / _check_maintenance

**有预留金额为什么可以恢复，却不可以重建？**

恢复只是重新开放受控写入口，保留既有预留，不需要重新推算预留。重建会重写投影，R2 又没有完整预留重建模型，所以要求预留为零。这是动作所需保证不同，不是同一个条件前后矛盾。

**恢复会用之前的报告吗？**

恢复在排他屏障内现场读取并核对，保存这次报告，不把前一份预览或离线报告直接当作当前准入。页面里旧报告仍可展示，但会明确标记过期。

**代码阅读重点**

比较 resume_workspace 与 apply_rebuild 的准入检查，再找 maintenance_freeze.resume_report。报告是恢复的组成部分，不是屏幕上临时的一句提示。

页面代码入口：resume, repair, verify

**面试深挖：怎样发现恢复条件过严**

用未来正常存在的非零预留和不可改的历史 WRONG_OWNER 作为反例，检查状态机有没有死路。测试必须验证能恢复且告警保留，而不只是测试条件越来越严。

**面试深挖：NORMAL 是什么承诺**

NORMAL 表示受控业务写入口可以尝试受理；每笔业务仍要重新过授权、幂等、锁和余额检查。它不表示所有历史意图问题已消失。

### 第12步：再核对一次：让健康结果有可检查的依据

重新导出当前数据库，离线核对结构、投影和支持的业务意图。对照之前的故障报告、修复日志与新报告。

### 术语与代码地图

**事务 / Transaction**

把多条 SQL 包成一起提交或一起回滚的单位。业务拒绝也可以正常 COMMIT，因为需要保存拒绝结果；异常回滚与业务拒绝是两件事。

代码：src/ledgerops/db/admission.py · _submit_once

**原子性与一致性 / Atomicity / Consistency**

原子性保证这批写入全成或全败；一致性还取决于规则有没有写对。完整地给错误商户记账仍可能原子提交，所以不能用“有事务”代替业务正确性。

代码：src/ledgerops/db/admission.py · _post_transfer；src/ledgerops/verification.py · _check_intent

**行锁与隔离级别 / FOR UPDATE / READ COMMITTED**

行锁让同一余额行的竞争修改等待；READ COMMITTED 不代表完全串行执行。项目在持有余额行锁后进行判断，并统一账户加锁顺序。十二步导览展示实际SQL；另设并发面板用独立连接观测真实等待关系。

代码：src/ledgerops/db/admission.py · _lock_balances

**业务 ID 与请求键 / Operation ID / Request key**

业务 ID 标识一笔业务；请求键在调用方和路由范围内标识一次逻辑请求。原身份重试返回原结果，复用原键却换内容报 409。新 ID 意味着新业务判定，不能拿来规避重复冲正规则。

代码：src/ledgerops/db/admission.py · _submit_once / _replay_by_request_key / _replay_by_operation

**重放与事务重试 / Replay / Retry**

重放读取已提交的业务结果；事务重试重新执行一个明确失败并回滚的事务。当前入口只对 40P01 / 40001 限次重试，未知提交结果用原业务身份恢复。两者不能混用。

代码：src/ledgerops/db/admission.py · _retained_result / _submit_with_retry

**分录与投影 / Journal / Projection**

分录保存不可修改的历史事实，投影是当前借贷累计和余额。读余额快，但必须能与独立分录重算一致；只有非负约束不能证明投影正确。

代码：src/ledgerops/db/sql/001_foundation.sql；src/ledgerops/verification.py · _check_projections

**核对 A 与 B / Projection / Request intent**

A 检查分录重算与余额相符；B 检查分录与保存的原始请求相符。原始请求本身若存错，B 也不可能凭空知道真实意图。

代码：src/ledgerops/verification.py · _check_projections / _check_intent

**工作区屏障 / Advisory transaction lock**

受控业务写事务拿共享屏障后读模式；维护拿排他屏障，等待在途事务排空。它依赖代码遵守相同协议，不自动拦截所有者的任意 SQL。

代码：src/ledgerops/db/admission.py · _open_admission；src/ledgerops/db/maintenance.py · _transaction

**投影代次与账户版本 / Projection epoch / Balance version**

epoch 标识工作区整体重建代次，version 标识单个余额行的更新版本。它们用来识别数据变化，不代表交易数量、货币金额或用户身份。

代码：src/ledgerops/db/maintenance.py · apply_rebuild / _write_projection

**延迟约束 / Deferred constraint**

事务中先插表头、后插明细会暂时不完整，所以在提交前检查最终形态：行数、总额和借贷平衡必须吻合。历史表头不可改，事后追加两行平衡分录也不能蒙混过关。

代码：src/ledgerops/db/sql/001_foundation.sql；src/ledgerops/db/sql/003_projection_maintenance.sql

**身份与数据库权限 / Principal / Database role**

Principal 是可信认证层提供的业务身份；数据库角色决定连接有什么 SQL 权限。这个课堂页面使用固定合成身份，没有生产登录。故障注入和正常业务调用的角色要分别看。

代码：src/ledgerops/db/admission.py · Principal；tests/conftest.py；lab/session.py · _opening / _reset

**一致快照与离线核对 / REPEATABLE READ / Offline verification**

导出在同一只读事务中读所有表，不拼接两个时刻。随后核对器只读完成的本地文件，不向数据库查询补数据。旧报告只代表旧快照，不自动代表当前状态。

代码：src/ledgerops/export.py · capture_snapshot / load_export；src/ledgerops/verification.py · verify_snapshot

**冲正与删除 / Reversal**

冲正写独立的反向业务和分录，保留原购买及所有失败尝试。同一工作区内，(workspace_id, original_operation_id) 限定最多一次成功；(workspace_id, operation_id) 标识每个尝试。失败不占用唯一成功名额。

代码：src/ledgerops/db/admission.py · _post_new_reversal；src/ledgerops/db/sql/005_full_reversal.sql

**SQL语句与绑定参数 / SELECT / INSERT / UPDATE / RETURNING**

SELECT读取记录，INSERT增加记录，UPDATE修改允许修改的行；RETURNING让写语句返回实际写入后的值。本项目把SQL里的%s占位符与参数分别交给psycopg，追踪也分开显示SQL与params；参数是数据，不是拼接进去的SQL语法。看一条语句时，先找表名，再找WHERE限制，最后看返回列。

代码：src/ledgerops/db/admission.py · _post_transfer / _finish_request；lab/trace.py · _start

**连接、游标与with / Connection / Cursor / Context manager**

连接是一条到PostgreSQL的会话；游标执行SQL并读取结果。Python的with管理进入与退出：with conn.transaction()包住整笔事务，正常退出提交，异常退出回滚；with conn.cursor()管理游标。dict_row让查询行按列名读取，便于写出balances[account_id]这样的业务代码。

代码：src/ledgerops/db/admission.py · _submit_once / _lock_balances

**自动提交与显式事务 / Autocommit / BEGIN / COMMIT / ROLLBACK**

本项目连接默认autocommit=True，目的是避免调用前已经偷偷开启一个事务。购买入口仍显式使用conn.transaction()，让多条SQL一起提交。故障注入的单条UPDATE在自动提交下自行完成，不一定发出单独的BEGIN/COMMIT文本，所以真实追踪里不能补画它们。

代码：tests/conftest.py · TestDatabase.connect；src/ledgerops/db/admission.py · _submit_once；lab/session.py · _drift

**主键、外键与CHECK / PRIMARY KEY / FOREIGN KEY / UNIQUE / CHECK**

主键标识表内唯一的一行，外键要求引用的记录存在，唯一约束禁止重复的键，CHECK限制一行可接受的值。它们各检查明确定义的关系；外键存在不能证明这就是请求指定的商户，非负CHECK也不能证明余额等于分录重算。业务ID和冲正关系还要注意workspace_id范围。

代码：src/ledgerops/db/sql/001_foundation.sql；src/ledgerops/db/sql/005_full_reversal.sql

**生成列与触发器 / Generated column / Trigger**

booked是由debits、credits和账户正常方向计算的生成列，调用方不能直接给booked赋值；修改累计借贷仍会改变它。触发器在数据库中执行额外检查，延迟约束触发器可在事务提交时检查最终分录。页面只观测客户端SQL，不展开触发器内部执行。

代码：src/ledgerops/db/sql/001_foundation.sql；lab/trace.py

**测试层次与反例 / Unit / Integration / Independent oracle**

单元测试验证金额与身份等局部规则；集成测试使用真实PostgreSQL和实际角色，验证事务、锁、约束和失败恢复。独立核对器不复用记账算法，故障注入主动制造漏更新或记错商户。测试通过说明已覆盖的输入与调度满足规则，不能推出所有未来并发和生产容量都已证明。

代码：tests/unit/；tests/integration/；reference/；src/ledgerops/verification.py
