# R3-PR01：独立持久支付商

依据：已采纳 [R3 合同](R3.md)，采纳提交 `eacbad9`。本片实现支付商协议和故障替身，
不实现账本 hold/派发/结果判定。后续交付仍按 [DELIVERY](DELIVERY.md) 推进。

## 实现与边界

`provider_sim/` 使用标准库，独立于 `src/ledgerops`；没有账本导入、共享数据库或运行时依赖。
SQLite 保留 namespace、请求字节、终局、唯一效果及签名历史；配置身份变化拒绝启动。
每个写入用 BEGIN IMMEDIATE，实际检查 DELETE/FULL/FK/busy_timeout。
同 key 同请求返回原事件；换请求 409；关单与支付串行，墓碑后不能执行。
ACCEPTED 可以显式推进 SUCCEEDED/FAILED；成功效果与成功事件同事务；终局不可反向修改。

HTTP 只监听127.0.0.1，以不同凭据区分正常请求和显式启用的故障控制面。
它是支付商测试替身，不能承担生产账本 HTTP 服务。生产服务的身份/授权、连接池和部署仍属 R5。
没有真实支付商、真实资金、真实用户认证或跨机器灾难恢复保证。

## 验收对应

| 条件 | 检查 |
|---|---|
| 持久身份、唯一效果、终局/墓碑 | SQLite实际连接测试 + HTTP子进程重启，独立SQL读取效果本金60/费用2/gross62 |
| 发送与关单双向竞争 | 提交前真实暂停门，观察控制状态后启动竞争方；两种顺序产生成功或墓碑 |
| 提交前/后崩溃 | 观察真实提交门后从父进程SIGKILL，重启同一文件并检查提交结果 |
| 不混用时钟/超时作金融结论 | 过期截止字段不让provider自行删除/取消；迟到PUT仍受持久key/墓碑裁决 |
| 签名与历史 | 独立HMAC验证；同事件查询字节相同；固定watermark分页不混入之后事件；分页证明绑定事件摘要 |
| HTTP边界与清理 | 错令牌/控制面隔离/重复JSON键/过大正文/错误Host等拒绝；正常SIGTERM与强杀场景清理自己子进程 |

故障控制的提交门不是业务请求字段。只有显式test-control模式和独立令牌才能配置暂停、
进程退出、滞后查询、pending终结或违约签名观测；正常启动不开放这些路由。
测试生成的矛盾观测不改支付商权威历史，用于后续验证账本的隔离逻辑。

## 来源与依赖检查

SQLite 官方 [rollback locking](https://www.sqlite.org/lockingv3.html) 与
[PRAGMA](https://www.sqlite.org/pragma.html#pragma_synchronous) 是事务/设置核查依据。
实际版本与生效值记录在本片证据中；这些设置和杀进程实验不替代断电/存储损坏试验。
Python 官方明确 [http.server 不推荐作为生产服务](https://docs.python.org/3/library/http.server.html)；
本片严格限于本地支付商替身，后续生产 API 使用独立的服务栈。
