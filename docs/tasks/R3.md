## 2. 冻结的金额例子与三个独立状态

以下分支各从“客户初始 100，购买 80”后的同一状态开始；失败与成功不是连续发生。
100 表示 PLN 1.00，本金 60、固定报价手续费 2、gross = 62。

| 阶段 | 客户 booked | 商户 booked / reserved / available | clearing booked | 新出金分录 |
|---|---:|---|---:|---|
| 购买 80 后 | 20 | 80 / 0 / 80 | 100 | 无 |
| 提现准入成功 | 20 | 80 / 62 / 18 | 100 | 无，只建立 hold 和意图 |
| 支付商已成功、本地尚未知 | 20 | 80 / 62 / 18 | 100 | 无，不冒充已经结算 |
| 取得权威成功并本地提交 | 20 | 18 / 0 / 18 | 38 | Dr 商户 62 / Cr clearing 62 |
| 另一分支：权威失败或关单墓碑 | 20 | 80 / 0 / 80 | 100 | 无，只释放 hold |

手续费由商户承担，支付商保存本金 60、费用 2、总出金 62；平台不确认手续费收入。
本金、报价手续费、报价/协议版本、商户、收款方、币种一旦准入就不能在重试时改写。
报价由合成本地配置校验，不把调用者随填的费用当可信报价；报价不是按恢复时的新费率重算。
未知旧提现未解决时，“换报价和新业务 ID”不是重试，可能造成另一笔真实业务付款。

| 维度 | 状态与约束 |
|---|---|
| 资金 | `HELD → CONSUMED` 或 `HELD → RELEASED`；每个 hold 只有一次终结。 |
| 认知 | `NOT_SENT`、`UNKNOWN`、`ACCEPTED`、`SUCCEEDED`、`FAILED`、`CLOSED_ABSENT`；矛盾另设粘滞 incident/停止标记，保留先前事实。 |
| 传输/工作 | 意图 READY/IN_FLIGHT/OBSERVING/DONE，尝试记录 MAY_HAVE_SENT、响应、超时、连接错误；这些不是资金终态。 |

`HELD+UNKNOWN` 和 `HELD+ACCEPTED` 都合法；`CONSUMED+SUCCEEDED`、
`RELEASED+FAILED/CLOSED_ABSENT` 是兼容终局。超时、500、暂态 NOT_FOUND、
进程死亡、重试次数耗尽、租约过期都不能单独产生 RELEASED。
本轮不做本地取消，因而不新增 `RELEASED+NOT_SENT` 写路径；原包允许的派发前取消留待后续。

矛盾停止范围是**该提现**的自动派发/资金判定，不自动冻结整个 workspace。
仍允许留存新的矛盾证据，禁止自动清除 incident、反向改账或重开 hold；
R3 不提供“强制判成功/释放/忽略矛盾”的运维操作，相关人工处置属于后续明确任务。

## 3. 支付商协议与持久身份（PR01）

独立进程、独立 SQLite 文件、独立命令/效果表；不读取账本数据库，不导入账本记账、
金额规范化、预期结果或核对帮助函数。共用标准库和公开协议文本不等于共用金额 oracle。

支付商 key 是带版本、无歧义编码的 `(provider_namespace, workspace_id, operation_id)`。
namespace/协议版本在准入时固定；本地收款方夹具将 beneficiary 绑定商户 owner。
规范支付商请求还绑定商户、收款方、本金、费用、gross、币种和协议版本，保存完整字节及摘要。
新请求键、重启、恢复轮次、尝试 ID 都不产生新 provider key。改变 namespace 是新业务域，
不能作为旧 UNKNOWN 的恢复捷径。保留整个场景生命周期的 key、效果、墓碑及事件历史。

| 接口（拟定） | 必须成立的协议 |
|---|---|
| `PUT /v1/executions/{key}` | 同 key/同规范请求返回已有状态；不同请求冲突。接受记录、唯一外部效果和成功终态的相应变更原子持久。测试可停留 ACCEPTED，之后用独立事务终结；不能出现成功终态无对应效果。墓碑后的 PUT 返回 CLOSED_ABSENT，效果数为零。 |
| `GET /v1/executions/{key}` | 返回有来源、序列、可见水位的签名观测；可故意滞后。NOT_FOUND 永远不是“未来不会执行”的证明。 |
| `POST /v1/executions/{key}/close-if-absent` | 带精确规范请求/摘要，在与 PUT 同一存储的 `BEGIN IMMEDIATE` 中串行：不存在则写永久墓碑；存在则返回原有 ACCEPTED/终局，不取消已接受执行。不同请求不能借关单重新绑定旧 key。 |
| 有固定 watermark 的历史读取 | 独立不可变事件历史，分页固定同一水位；供崩溃恢复/证据核对。不是与 PostgreSQL 的分布式快照，也不在 R3 生成 R4 的结算分组文件。 |

关单与 PUT 竞争必须测两种顺序：关单先赢，迟到 PUT 永不执行；PUT 先赢，
关单返回已有执行，pending 不被当 absent 释放。FAILED 的协议含义也必须是该 key
永久无成功效果且不会后来执行，不是一次 HTTP 失败。合同违约观测只能由隔离的测试控制面注入。

**与原包 WAL 默认的有意差异：** 本提案建议 SQLite rollback journal `DELETE`、
`synchronous=FULL`、`foreign_keys=ON`、有限 busy timeout；读写竞争接受串行等待。
保留 `BEGIN IMMEDIATE` 的权威写事务，不把 WAL 当吞吐要求。
实施 PR01 时记录实际链接 SQLite 版本、文件系统与 PRAGMA 生效值，核对适用的官方缺陷/修复。
原包 L-EXT2 的并发 WAL 修复版本门槛不应被 Python 版本替代；若以后选择 WAL，
必须另外核查该门槛和当前适用修复并补对应测试。本提案没有检查当前 SQLite 是否合格，
也不声称 DELETE/FULL 能证明任意断电、损坏或银行级持久性。

reset 必须创建新文件/namespace 并显式保留旧场景证据，不能删除旧 provider 文件后继续恢复旧提现。
PR01 可只操作独立支付商，不加 PostgreSQL 迁移或账本金融路径。

## 4. 准入、hold 与保守派发（PR02）

### 4.1 身份、授权和不可变回执

扩展类型化提现命令与 `payout:v1` 请求路由。沿用 `Principal(workspace, client, actor)`，
受信调用边界提供身份；新提现核对商户账户 owner、类别/币种、enabled、收款方绑定与报价。
知道 UUID 不等于权限；重放也核对保存的业务归属，不能换一个自己账户去读取别人提现。

本提案沿用原包的**202 受理回执**，而非把它写成 201 支付成功：
ACCEPTED 表示 hold 和 READY 意图已提交；回执只含稳定业务/提现 ID、
`accepted_for_processing`、固定金额及协议版本等，不含可变余额或“当前支付成功”。
账本尚无生产 HTTP 服务，202 是 `AdmissionResult.http_status` 的契约数值；不承诺已存在 status URL。
另设经同一商户归属检查的只读状态查询，返回当前 hold/knowledge/工作状态与证据引用。

现有 SQL 只允许 201/422，且 `_finish_operation` 把非 201 当 REJECTED：
PR02 必须用**新迁移**显式允许 PAYOUT 的 ACCEPTED/202 与 REJECTED/422，
保持购买/冲正的 201/422 限制和原结果不变；请求表、路由、解析、终态检查、重放与核对一起扩展。
不能让 `IN_PROGRESS` 跨事务存在，也不能把旧 operation.response_body 改成后来支付结果。
原业务/请求键重放始终返回原 202，即使查询状态已经 SUCCEEDED 或 FAILED。
不足/界限拒绝保留 422；409 身份冲突、404 授权拒绝不伪装成支付商失败。

### 4.2 冻结资金与意图在一个事务提交

沿用空闲 autocommit 连接、Python 显式 READ COMMITTED 事务和提交后返回：

1. 共享 workspace 屏障 → 检查 NORMAL → 归属/输入规则。
2. 先抢请求键，再抢业务 ID；旧身份走同一重放/冲突规则。
3. 新业务锁商户余额，检查 `available >= gross`、金额/累计/version 界限。
4. 写不可变 payout 指令、reservation HELD 及首个事件；原子增加 reserved/version，
   不写出金 journal，不修改 debits/credits。
5. 同事务创建唯一 READY 意图，保存 operation 与 request 的 202 后提交。

任一步或 COMMIT 失败，整组回滚；未知 COMMIT 由同一业务/请求身份查询或重放恢复。
同操作/新请求键至多增加关联，不重复 hold 或意图。已保存的拒绝不因之后补款变成功。

新增 hold 实体/不可变事件是权威生命周期，`reserved` 是所有 HELD gross 的投影和，
不是独立可随意累加的真相。复合 FK、唯一约束、合法状态/终结约束、终态所需 hold/intent
的延迟完整性检查和逐列权限必须跟随新迁移一起审查；Python 仍负责业务归属与具体金额。
约束不独立证明投影正确。新表不能让未完成准入、无 hold 的已受理意图或双重终结安静提交。

### 4.3 先记录可能已发送，再联网

候选读取不持有行锁；claim 事务重新检查候选，先锁 operation/payout，再锁 intent，
写 attempt 的 MAY_HAVE_SENT，knowledge 置 UNKNOWN，意图置 IN_FLIGHT/OBSERVING，提交后才联网。
没有成功提交 claim 不得发 PUT；claim 成功但实际未发送就崩溃，也按未知处理。

每次主动传输轮次最多五次同 key/同字节尝试，退避与抖动有上限；之后转入有界观察调度，
每轮扫描/网络调用数和下一次到期时间有限，不忙循环，不把次数/时间当业务终局。
首次新业务准入时将配置产生的派发截止时间固定进不可变 payout 指令与支付商请求；
客户端业务规范字节不包含这个服务端生成时间，同一业务的重放读取原指令、不重新计时。
恢复已有 MAY_HAVE_SENT 的工作先查证。截止前遇到 NOT_FOUND、超时或连接错误，在有界调度中
用同一个 provider key、同一请求字节重发 PUT；不创建新业务或重新报价。得到 ACCEPTED 则继续观察，
得到权威终局则判定，不因继续调度而覆盖它。截止后不再新发 PUT，转为同身份 close-if-absent；
关闭能力不可用时保留 UNKNOWN/hold。截止只决定是否申请关单，不是 FAILED 或释放证据。
支付商不因请求里的时间过期自行取消已接受执行；截止前已在途的 PUT 仍可能在关单前赢得串行竞争。
使用可注入 UTC 时钟，记录截止与调度时间；可用性受时钟偏差影响，但不会因此绕过墓碑释放规则。
本轮以单工作循环为起点，仍用数据库 claim 防重复领取；重启/重叠旧调用可能重复传输，
最终靠同一持久 provider key 幂等，而非承诺任意时刻只有一个网络请求。
旧 attempt/过期 claim 的迟到更新必须在 operation→intent 锁内重验当前状态与 `last_attempt_id`；
可以追加自身传输事实，不能把 DONE、终局或 incident 改回 IN_FLIGHT/UNKNOWN。
过期 attempt 携带的有效支付商证据仍交统一观测入口判定，不因旧 worker 身份而丢弃终局事实。

数据库整事务重试与支付商传输重试分开：前者沿用只对确定回滚的 40P01/40001 最多三次。
联网不得在准入/claim/观测的 PostgreSQL 金融事务里，更不能塞进整个数据库事务重试体。
超时、取消、断线的既有语义不放宽；异常不能作为 422 业务失败吞掉。

## 5. 观测、认证和一次本地终结（PR03）

支付商响应、lookup、close 和 callback 都经同一观测校验/判定路径，传输成功不直接改钱。
本地测试 HMAC 使用显式 key ID、原始签名字节、恒时比较与消息长度上限；
秘密不进入规范请求、导出或证据日志。绑定 namespace、workspace、key、请求摘要、商户、
beneficiary、本金/fee/gross、币种、协议版本、event ID、source sequence 与支付商 issuer。
由固定配置选择可信支付商/密钥，不能信任消息自报的 actor 或一个未验证的 provider 名称。
认证代表此模拟协议的权威，不代表银行真实付款证明或生产密钥管理。

持久保存已认证原文/摘要、来源、序列和接收记录；无效签名/身份/金额/摘要进入有大小与数量
边界的隔离/拒收记录，不产生金融效果。相同 event ID/相同字节幂等；相同 event ID/不同字节
保留两份有界冲突证据并产生 incident，不能被主键冲突吞掉。未认证消息不能借此停掉合法提现。
同一支付商逻辑事件通过 callback/PUT 响应/lookup/close/history 到达时，event ID、序列和签名字节
保持相同；接收通道仅作为独立元数据，不混入该签名事件的 issuer 或改写事件字节。
暂态 NOT_FOUND 没有已接受请求/执行金额可供断言：它只能绑定查找上下文、key、签名 issuer 和
可见水位，报告暂态缺失，不伪造一份已接受执行；完整字段/请求摘要一致性是金融终局证据的门槛。

| 证据 | 本地动作 |
|---|---|
| 新、兼容的 ACCEPTED | 保留 HELD，推进认知/观察进度，不记出金。 |
| 权威 SUCCEEDED | 同事务写观测与终局事件，Dr 商户 gross / Cr clearing gross，消费同一 hold、reserved 减 gross，更新相应累计/version，意图 DONE。 |
| 权威 FAILED/CLOSED_ABSENT | 同事务写观测与终局事件，释放同一 hold、reserved 减 gross，意图 DONE；无出金分录。 |
| 重复兼容终局/旧非终局 | 可以记录接收，资金不再变化；不将最终认知降级。 |
| 不兼容的已认证终局，或同事件换字节 | 保存 incident，停止该提现自动处理，保留最后已提交资金状态。即使矛盾终局序列更旧也不能忽略。 |

同一 hold 最多一个 CONSUMED/RELEASED 终结；成功终结至多一张绑定该提现 operation 的 journal。
不能消费后再释放，也不能释放后面对违约成功就自动补记/透支；这些是需调查的外部矛盾。
判定、hold 事件、余额、journal、意图终态、有效观测绑定同一个 PostgreSQL 事务，
在插入观测后/终结中间/提交处故障必须全部回滚；重新提交观测后只能产生一次效果。活动 hold 的漂移修复后再观测成功，必须达到 18/0/18、clearing 38。

已有外部成功即使商户后来 disabled，也必须尝试记录，不套用“新购买/新冲正”的 enabled 门槛。
clearing 是借方正常资产账户，成功提现给它记贷方，不能直接复用只认两类负债的 `_lock_balances`。
实际文本/实现统一使用 `SYNTHETIC_CLEARING`，不得因教学简称而选错账户。

既定单次/累计金额与 version 上限仍成立。准入和派发前预检本地结算容量，
但不声称它能排除并发耗尽/损坏；支付商已经成功而本地因界限、缺投影或约束失败无法提交时，
不得转成 FAILED 或释放。支付商历史保留该事实，本地保留原 hold/待观察状态，
记录可持久化的错误/incident 后停自动资金处理；恢复进展条件必须明确排除此未解决障碍。

## 6. 全局锁序、维护模式与真实外部事实

所有新的账本写入口先拿与 R1/R2 **同一个**共享 workspace advisory 屏障并读模式。
本提案在 FROZEN/RESTORE 不执行新准入、claim、观测落库或金融终结；返回可重试结果，
不确认已持久接收。支付商保留事件并允许回调重投/恢复后 lookup，不能把被挡住的回调当处理成功。

| 路径 | 共享屏障/模式之后的锁序 |
|---|---|
| 新提现准入 | request key → 自己的 operation → payout/intent（如已有）→ 商户余额。 |
| claim | 自己的 operation/payout → 自己的 intent；不先锁候选 intent 再反向等 operation。 |
| 观测/终结 | 自己的 operation/payout → intent → merchant/clearing 余额按账户 UUID 排序；不抢 request key。 |
| 购买/冲正/重放 | 保留现有顺序；冲正仍先锁原购买再锁排序余额，提现不锁别人的购买。 |
| 维护 | 同 key 的排他工作区屏障 → 维护检查/写入；不在持有余额时反向请求排他屏障。 |

余额是共同末端，异步回调不反向抢请求键，工作领取不倒置业务/意图锁序。
这解释命名的混合调度为何不形成循环，并由实际 PostgreSQL 等待/终止测试支持；
它不是任意后来代码、任意调度绝不死锁的证明，确定回滚的死锁仍按有界规则处理。

冻结排空的是合作协议下的**数据库写事务**。claim 已提交的进程可能正准备发送，
网络请求和支付商自治执行可以在冻结后继续成功。不得通过再次读 mode 承诺消除这个时间窗。
持久 hold 不因此释放；恢复 NORMAL 后重新观察，消费或释放必须依据权威证据。
所有者任意 SQL 不在屏障保证内，R3 不实现外部支付暂停/全局停机协议。

## 7. 导出、独立核对与重建接口

当前 v4 严格对应 SQL 001–005，未知表/业务/状态会被拒绝，不是可直接添加字段的容器。
PR02 增加提现/hold/intent/attempt 时拟新增 **v5**；PR03 增加观测/incident/终结协议时拟新增 **v6**。
每个新格式显式列出迁移集合、完整关系/字段、金额/字节编码与报告能力。
不要直接覆盖 v4 的 schema 列表；v1–v4 的已发布包继续可读/可核对，v6 也须继续接受 v5。
具体新迁移编号与文件名在各实现任务确定，本轮不创建占位迁移。

账本导出沿用 reader、同一 REPEATABLE READ READ ONLY 快照、规模限制与原子文件发布；
包括提现固定指令、hold 全生命周期、派发/尝试、观测/隔离事件与终结引用，不导出密钥。
支付商文件/历史用自己的 namespace 与固定 watermark 导出；不能把两份独立导出称为同时快照。
跨存储的恢复断言依据固定身份和明确因果断点，而非“两个导出数字碰巧相等”。

独立核对不导入生产准入、支付判定或金额帮助函数，扩展以下维度：

- 结构：作用域/账户类别/金额界限、hold 事件合法连续、至多一次终结、意图与效果引用完整。
- A：分录重算 debits/credits/booked；新格式再独立折叠 HELD gross，与每个账户 reserved 比较。
  合法的非零预留不再是“不支持”；缺/重复/错账户 hold、少更新 reserved 必须被发现。
- B：解析准入前保存的规范提现指令，比对商户/收款方/fee/gross/provider key、202/422 回执、
  hold/意图和最终出金/无出金规则；拒绝不根据今天余额重判。手工清单仍额外检查请求捕获。
- 外部证据覆盖：区分“账内事件相互符合”“存在匹配签名观测”“支付商独立效果/历史符合”。
  没有独立支付商证据时不声称已经证明外部实际支付；正常 HELD+UNKNOWN 也不能叫支付完成。

PR02 的报告必须注明“外部终局尚未实现”，不能把只查 hold 的 healthy 宣称为 R3 验收通过。
PR03/04 增加覆盖与待解决/incident 分类；UNKNOWN 可以账内一致，但仍需要查证。
旧版本报告维持旧能力范围，不因新核对器而伪造旧包中的 hold/外部证据。

维护继续使用冻结后的现场分录重算，不增加候选代次或目标余额输入：

- 从 PR02 的新 hold 格式起，`apply_rebuild` 要求结构（含 hold 生命周期合法）和 B 通过；
  在同一排他事务中从 journal 重算 debits/credits，从活动 HELD 事件独立重算 reserved。
  只改余额投影，保留 hold 与全部事件，不再要求 reserved 为零。目标 booked 必须覆盖目标 reserved；
  若权威来源自身矛盾则拒绝修复，不能靠清零、删 hold 或透支来通过。
- 修复审计原子记录 reserved 前后值以及全部余额/epoch 变化，提交前用独立核对器复验。
  旧格式 v1–v4 缺少权威 hold 历史，仍按旧语义拒绝非零预留重建；历史修复记录不改写。
  新迁移必须扩展现有修复审计的零预留限制，记录修复算法/来源版本，核对器按记录版本解释。
- `resume_workspace` 仍只要求结构/A；A 在新格式包括 reserved 投影与 hold 和相等。
  合法非零 hold 允许恢复，B/未解决外部认知/incident 如实进入恢复报告，
  不自动清除提现的粘滞停止标记。余额漂移仍阻止恢复，但现在能先重建投影解除它。
- `reservation_supported` 与 `rebuild_eligible` 明确区分旧格式不支持、新格式支持且来源合法；
  未知版本/非法 hold 生命周期不能因为金额为零就通过。能力来自完整的权威来源而非余额表数值。

此修改解决具体循环：活动 hold 62 + 投影漂移 → FROZEN → A 不通过无法 resume，
旧零预留门槛又禁止 apply，冻结还阻止终结 hold。现在先从分录/hold 来源修好投影，再恢复和查证。

## 8. 原设计假设与当前实现的差异

| 原包假设 | R1/R2 实际实现及 R3 处理 |
|---|---|
| 记账/领取/观测均在 SECURITY DEFINER 入口，运行角色无私表 DML | Python 显式事务 + 手写 SQL；`ledger_app` 有限定直接 DML。新流程沿此边界，审查逐表/逐列权限及独立检查，不恢复旧数据库函数架构。 |
| `ledger_private` / `ledger_api`、Alembic 式路径、API 路由已规划 | 实际是 `ledger` schema、`db/sql/001…005` 校验和迁移、Python 入口，没有生产 HTTP/auth 服务；新代码路径是未来实现，不冒充已有模块。 |
| 整个准入可直接接 payout 202 | 当前类型/路由、授权、`_parse_stored`、`_retained_result`、`_finish_operation` 与 SQL 都是购买/冲正语义。必须显式分派新类型，禁止落入“不是购买就是冲正”的 else。 |
| 通用 posting primitive 可处理提现 | `_lock_balances`/`_post_transfer` 只处理客户与商户负债；提现新增 merchant/clearing 规则，复用事务/身份框架，不复制 `_submit_once`。 |

| committed journal 仅靠平衡/append-only 片段 | 实际表头声明行数/总额并封存，阻止事后追加成对行。提现成功分录保持封存和一业务一 journal；hold 不是 journal。 |
| 原交易引用本身 UNIQUE，反转列即唯一性 | R2 已用独立成功冲正关系保证 success-only 唯一；失败尝试都保留。提现不改此规则，也不把支付失败当内部冲正。 |
| shadow generation/候选激活 | R2 已改为排他事务现场重算 + 修复日志/epoch，不建候选表。R3 保留该设计。 |
| 原包重建/恢复还要求另行停止 dispatch | R2 只实现账内合作写者排空，没有物理停止外部付款；R3 保留 claim 提交后的外部时间窗与观测重试，不冒充 R5 的独立派发禁用/恢复协议。 |
| 恢复与重建可以共用全部准入条件 | R2 独立修正为 resume 结构/A，apply 结构/B/零预留；R3 新格式把 apply 扩为结构/B/合法 hold 来源，避免活动 hold 与漂移形成维护循环。 |
| 日志/导出/检查表可直接覆盖 schema 列表 | 已实现 v1–v4 严格映射和旧包兼容；R3 必须新增格式、独立新表权限及旧格式回归。 |
| 支付商默认并发 WAL | 本提案第 3 项建议先用 DELETE rollback journal；需用户确认，实施记录实际 SQLite 能力，未声称已验证任何版本。 |
| 原包测试/模块/恢复步骤已经存在 | R1/R2 测试证明其既有边界；L-EXT 实验仍待实现。R5 旧备份缺历史恢复、R4 结算单等不计入本轮。 |

## 10. 故障矩阵与缺陷检测

用进程间屏障/明确 failpoint 确定顺序；超时只是卡死保护，不靠 sleep 推断是否提交。
本地数据库断线前后 COMMIT 都可能未知，必须检查真实存储，而不是按没收到响应判回滚。

| 场景 / 映射 | 必须观察到的结果 |
|---|---|
| 准入在 hold/投影/意图/回执各步异常；COMMIT 断线 | 回滚后全无或提交后全有；原身份恢复一个 hold/intent，无 orphan。 |
| claim 提交前退出 | 未提交 MAY_HAVE_SENT，不得存在该次网络发送。 |
| claim 已提交、发送前退出（L-EXT1） | 本地 UNKNOWN+HELD；恢复先查证；截止前同 key 重发，截止后关单，不能根据“测试知道没发”走特权释放。 |
| provider 提交前退出 | 重启查实际存储；若 absent，也须权威关单才释放。 |
| provider 已成功、响应丢失/ledger 进程退出（T-EXT-04） | 独立 provider 效果存活；本地 hold 62 不变；恢复按同 key 查证，一次出账到商户 18/clearing 38。 |
| 成功被滞后 NOT_FOUND/500/超时遮住（T-EXT-01） | available 始终 18，直到权威证据消费；不得增回 80、重建新 key 或用重试上限判失败。 |
| 截止前 NOT_FOUND → 重发；截止后 PUT 与 close 两种竞争、已有 pending（T-EXT-02） | 可注入时钟验证截止前重发成功 18/0/18；截止后墓碑先赢 80/0/80、迟到 PUT 零执行；PUT 先赢最终 18/0/18；pending 不能被释放。 |
| 观测插入后、余额/hold/分录/意图中途、COMMIT 故障 | 金融终结原子；重投/查询消除未知，一次消费或释放。 |
| 重启后新 worker 已终结，旧 attempt 响应才到达 | 旧 attempt 只补自身传输事实，不倒退 DONE/终局或清除 incident；有效终局仍经统一入口去重/查矛盾。 |
| 重复/旧序列/同事件换字节/旧矛盾终局（T-EXT-03） | 幂等、隔离或 incident 符合第 5 节；矛盾不自动释放/补账。 |
| 错签名、未知 key ID、跨域/key/digest/商户/收款方/金额/币种错误 | 无金融效果、不泄露他人状态；有界可检查拒收证据；未认证消息不能冻结合法工作。 |
| 购买/冲正与 hold/终结同账户竞争 | 实际等待后 booked>=reserved；每个可用余额决定符合其顺序；终值与独立模型/hold fold 一致。 |
| 回放/claim/观测与 freeze 交错 | 合作写事务被排空；FROZEN 不写新状态；外部可继续成功，NORMAL 后重新观察；冻结不被描述成付款停止。 |
| disable 后返回成功；本地累计/version/投影障碍 | 停用不抹除外部事实；可提交时正常消费，不能提交时保留 hold/证据并停自动判定，不伪造失败。 |
| 权威关单不可用、证据永不出现（T-LIVE-01 边界） | 明确 unresolved/age/reason，不伪造收敛；故障停止且终局可取的另一些案例才有界完成。 |

至少临时注入下列缺陷，并要求**目标业务断言失败**：超时/NOT_FOUND 释放；重试换 provider key；
hold 与意图分事务；消费与 journal 分事务；忽略旧终局矛盾；吞掉同 event 不同字节；
遗漏 reserved 更新；异步路径绕过工作区屏障。语法错误、fixture 失败、超时或进程卡住不算杀死变异。

## 12. R3 不能证明什么

- 强关单/墓碑、终局失败不可再执行和持久 key 是**此模拟支付商的协议前提**，
  不是任意真实支付商具备的语义。缺少负面权威时可能长期冻结 62，安全不意味着可用性无损。
- 命名断点、受控调度和真实 kill 只证明记录的矩阵；不保证任意故障时序、无限并发、
  任意调度无死锁、系统级 exactly-once 或任意灾难下恢复。
- 独立进程/存储、SQLite 事务与 FULL 不等于独立机器故障域、真实电源故障或磁盘损坏证明。
  本地 HMAC/合成身份不等于生产认证、真实收款人授权、密钥管理或银行资金事实。
- A/B/hold 相符不证明最初请求捕获正确，不把签名本身当支付商一定守约；矛盾必须保留。
  两存储独立导出没有分布式原子快照。
- PR04 的恢复前提是**本地准入/身份/hold 历史仍完整，支付商领先于本地处理**。
  从旧备份丢失业务指令、provider namespace/密钥或历史归档的恢复属于 R5，不能盲目重派发。
- 有界恢复还要求 provider 的权威终局可取得、本地数据库可写且数值/version 容量及数据完整性满足。
  对永久 UNKNOWN、矛盾或本地容量障碍只能诚实保留 unresolved；不保证全部案例最终自动完成。
- 不包含 R4 结算对账/吞吐实验、真实支付合规、生产容量、HA 或已完成用户个人掌握评估。
