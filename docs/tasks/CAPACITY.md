# 容量切片：完整流式证据与维护贯通

用户要求完成剩余路线并处理真实运行问题。本切片保留001–010迁移及历史格式，修复两个实测问题：
两个提现各保存65/64条64KiB隔离记录，会超过旧16MiB传输上限；旧分组十六进制正则在重复大记录上
造成约566MB峰值。只提高常量不足以解决这两件事。

交付采用独立format10：单一RR只读快照、命名游标有界读取、不可变分块/完整清单；标准库SQLite核验
全部源数据、全局投影/hold与请求、完整语义闭包。老格式1–9维持原有能力。未知版本、缺块、数据不全、
磁盘/内存或闭包预算不足，都不能返回健康结果。

R4使用明确的FINANCIAL_STREAM10_COMPACT_V1：完整原始块永久RUN pin，完整核对报告绑定源摘要；
精简匹配视图只作为索引。审批重建原始块、复核完整数据，并重算比较视图，不把省略的历史当空表。
一个有正常外键、却错误挂在PURCHASE下的payout记录曾绕过按类型选择的闭包；独立变异测试已复现，
全局业务类型约束用于防止此类记录被漏查。

操作入口为cli export/verify --format stream10、recon_cli match/publish --source-format stream10。
新匹配入口仅支持workers1，拒绝2/4；旧R4多进程行为和实测保留。稳定run_id、提交结果未知和无旧版本
回退均须由真实数据库验证。

维护贯通另以小切片接入同一完整核验：冻结排空后，在已有排他屏障/READ COMMITTED事务内核验，
不在等待锁之前固定旧RR快照。大型内部核验/预览明确标识其捕获上下文；不能冒充公共RR证据。
新上下文的预览暂不用于R4/R6。重建仍现场SQL重算、独立后验、余额/修复记录/epoch同事务提交；
恢复仍只要求已核实的结构和A，B问题保留报告。

验收覆盖超过10,000请求键、129条最大隔离记录、跨块并发提交、最后一条请求篡改、错误商户、
错误业务类型子记录、缺块/重算摘要后的篡改、未发布目录、实际SQLite空间耗尽、真实CLI、R4全块发布/
审批及维护全链路。独立进程峰值和Linux磁盘边界分别实测，不从单个样本推断吞吐或最大容量。

有限边界：源256MiB/100万行，普通块1MiB/单行最多4MiB，SQLite主索引512MiB/缓存2MiB，
语义闭包16MiB，匹配视图16MiB。还需要SQLite临时工作空间；这些是拒绝上限，不是服务SLO或磁盘配额。
