Date: 2026-10-27. Status: **proposed; decisions pending; no R2 code authorized by this document**.

## 1. Outcome, sources and scope

R2 must establish three bounded capabilities:

1. Materialize a consistent workspace export and independently check posted balances
   and original business intent, reporting the guarantees separately.
2. Drain cooperating database writers, rebuild a candidate projection while frozen,
   validate it and activate it atomically with inspectable before/after generations.
3. Reverse one successful internal purchase in full, with stable retained outcomes,
   arbitrarily many rejected attempts and at most one successful reversal effect.

Sources read: current repository HANDOFF, PR04 task, admission module, schema,
independent R1 fold; Vault working blueprint rev 1 L-DB3/L-DB4/L-REV1 and R2 slices;
the user's 2026-10-27 instructions and independent R1 review. Original files under
`docs/reference/` remain historical and unchanged. This contract resolves missing R2
mechanics as proposals; it does not silently treat reference instructions as approval.

No R2 implementation, tests, fixtures or migrations are created in this round.
There is no push, deployment, tracker update, Chronicle change, HTTP/authentication
adapter, external payout, partial refund, chargeback, online rebuild or R5 approval.
The existing R1 behavior and tests remain the regression baseline.

## 2. Invariants and independent evidence (decision 1)

Keep these separate in every report:

| Claim | Evidence required | Limit |
|---|---|---|
| Structural journal validity | Headers, complete entries, scope references, declared counts and both side totals | Balanced entries can still target the wrong owner. |
| Projection consistency | Independent integer fold over all accounts/entries, compared with complete live projection rows | Agreement with a wrong journal is possible. |
| Command fidelity | Independently frozen command manifest/model, matched to canonical operations, journal accounts/amounts and outcomes | A manifest reconstructed from SUT output is not independent evidence. |
| Reservation correctness | Authoritative reservation events/lifecycle | Not available in R2; never inferred from posted entries. |

Extend the small reference implementation with an independent single-threaded
command model, including accepted/rejected purchases and full reversals. It must
not import production posting, canonicalization, money, SQL builder or reconciliation
helpers. Expected ownership, amounts, original IDs and allowed outcome sets are
prepared before running the SUT. Generated command inputs/seeds may be recorded;
they do not reproduce operating-system/database scheduling.

Verifier input is plain versioned export data plus optional independent command
manifest. Count zero-activity accounts explicitly. Compare debit/credit totals,
booked balance, account sets and scope; validate empty/missing journal headers as
well as entries. Verify request/operation payload/result bindings, one financial
effect for accepted purchases/reversals, no effect for rejected operations, and
successful reversal relation cardinality and directions.

Reports distinguish projection drift, missing/extra account, incomplete/invalid
journal, wrong owner/amount, missing/unexpected effect, inconsistent outcome,
reversal-relation violation, unsupported reservation, corrupt/incomplete input and
unverified business intent. Report expected/actual IDs and fields; omit credentials.
Never label an absent independent manifest as complete business verification.

Rebuild is eligible only when immutable source structure is valid and independent
command fidelity passes for the exported scope. Missing/incomplete command coverage
or a wrong-owner journal blocks activation. A projection-only defect is repairable;
a wrong business journal requires a separate reviewed corrective business action,
not editing journal history or regenerating intent from the wrong output.

## 3. Consistent export v1 (decision 2)

Use one `REPEATABLE READ READ ONLY` transaction for each workspace export. Pin the
snapshot with the first read and use the same connection/transaction for every row.
Do not concatenate exports from independently started statements/transactions.
Ordinary diagnostic exports may run under NORMAL; they describe their pinned state,
not necessarily the state when the file finishes writing. Rebuild inputs must be
exported afresh after freeze has drained writers.

Export a bounded local UTF-8 JSON bundle with a versioned manifest and deterministically
ordered data: workspace/mode/epochs, accounts, balances, operations, request results,
journal headers/entries, reversal attempts/success relation when present, and relevant
freeze/rebuild identities. Filter every relation by the same workspace. Retain raw
canonical payload bytes with a documented lossless encoding, SHA-256 payload values,
immutable responses and timestamps. Monetary fields use canonical decimal integer
strings, not JSON floats; IDs and enum/status/null representations are explicit.
Never include connection strings, passwords or authentication secrets.

The manifest declares format version, export UUID, workspace UUID, schema version,
Git code revision and dirty flag, frozen input-manifest identity/coverage if supplied,
projection epoch, freeze identity if applicable, data member names/counts, exact
byte sizes and data integrity digests. Capture transaction snapshot metadata as an
opaque witness, not a portable resume token or a wall-clock cutoff. Timestamps alone
are not an export membership boundary. Input scale/byte limits are documented and
checked before claiming success; a large input cannot be silently truncated.

Only after all rows are materialized successfully: write a unique sibling temporary
directory, flush data and manifest, validate declared members/lengths/digests, then
atomically rename on the same local filesystem to a fresh final export UUID and
flush the parent directory. Consumers reject temporary, unknown-version, duplicate-
key, unexpected-member, incomplete, corrupt or cross-scope bundles. Never overwrite
an old completed export. A crash before publication leaves an unpublished temporary
bundle; cleanup targets only recognized abandoned temporary paths, not arbitrary files.
This is a bounded single-host filesystem protocol, not the later R4 DB/object-store
publication and GC protocol. Data hashes check bytes, not source truth or command intent.
No new SHA-256 source-code inventory is introduced; use Git for code identity (§8).

## 4. Freeze, candidate generations and activation (decision 3)

### 4.1 Roles and writer contract

Preserve `ledger_app` business permissions and original journal guards. Add a
separate least-privilege `ledger_maintenance` role for declared maintenance metadata,
workspace mode changes and projection repair; it owns no financial schema, has no
DDL/trigger-disabling/superuser authority and is not a member of the migrator role.
Verification/export use separate read-only credentials, not the owner role.
Migrations remain owned by `ledger_migrator`, added as new checksummed migration
files; never rewrite applied `001_foundation.sql`.

Every cooperating mutator, including reversal, new request-key association/replay,
and administrative account/funding fixture paths used in an integrated schedule,
takes the existing transaction-scoped shared workspace lock before mode or writes.
The exact key remains `hashtextextended('ledgerops:workspace:' || workspace_uuid::text, 0)`.
Hash collisions only serialize unrelated workspaces. Raw service-credential SQL and
DB owners remain declared trust boundaries; advisory locks are cooperative, not a
claim that mode revokes all SQL writes. No network/provider I/O inside a transaction.

### 4.2 Freeze protocol

Maintenance requires an idle autocommit connection and explicit READ COMMITTED
transaction, just as R1 admission owns its transaction. Acquire the **exclusive**
workspace advisory lock before reading/changing mode and before any lower-order lock.
This waits for all shared-holder transactions to commit/roll back. Under the lock,
require NORMAL, create a durable freeze identity/token with a monotonic maintenance
epoch and actor/reason, change mode to FROZEN, then commit. Lock timeout/connection
ambiguity cannot be reported as a completed freeze. Idempotent maintenance retries
use the same token and inspect the committed record; they never overwrite a different
freeze session. RESTORE is a different mode, not interchangeable with FROZEN.

New business writers then acquire their shared lock, see FROZEN and return retryable
503 with no claims/effect. Existing shared holders finish first. Tests must mutate
away the shared-lock hook and demonstrate that the drain assertion fails.

**Freeze means cooperating database business writers are drained and new ones are
refused. It does not mean external payments have stopped.** There is no provider in
R2. From R3, already-sent requests can still succeed; in-flight/possibly-sent cases
remain unresolved pending authoritative provider evidence. Database mode cannot
manufacture cancellation or non-execution proof.

### 4.3 Build and validate a candidate

After durable freeze, export afresh from one snapshot and bind it to the current
freeze token/maintenance epoch/projection epoch. Generate an immutable candidate
ID and complete candidate rows, including zero-activity and missing-projection
accounts, in separate generation storage. Keep failed candidates and diagnostics
inspectable; never mutate an old candidate into a different answer.

Proposed storage is generation metadata plus generation rows; the existing
`account_balance` remains the operational projection. A generation records source
export identity, independent manifest identity, base epochs, before/candidate role,
validation outcome and counts. Candidate storage receives no ordinary runtime writes.
Use explicit lifecycle transitions; incomplete candidates cannot become validated.

R2 has no authoritative reservation events: export/report actual `reserved`, but
refuse activation if any exported/current reserved value is nonzero or reservation
history is unsupported. Do not guess reservations from journals, reset them, or
mislabel posted-balance consistency as hold verification. Reservation-only synthetic
fixtures may exercise reversal availability; they cannot pass the rebuild gate until
explicit fixture cleanup returns reserved to zero. R3 must amend the export/fold/gate
contract when reservation events exist.

### 4.4 Atomic activation and explicit resume

Activation again takes the exclusive workspace barrier, requires READ COMMITTED,
FROZEN and the exact current freeze token/maintenance epoch. Check the candidate's
base projection epoch with compare-and-set semantics. Under this exclusion, compare
fresh immutable source sets and the complete independently checked fold/command
results with the candidate; do not rely on old counts, a file hash or a past mode read.
Any intervening maintenance/account/source mutation invalidates the candidate or
must fail this recheck. Diagnostic evidence of pre-existing projection drift is kept.

Within **one transaction**: preserve all current operational rows as the before
snapshot, copy the entire validated candidate into `account_balance` (insert missing
legitimate accounts, update existing accounts), advance the projection epoch and
mark this candidate activated. Do not write generated `booked` directly. Validate
complete account-set equality and post-copy totals before COMMIT. No table rename,
per-request dynamic table selection or dual-writing protocol is introduced.

This is a logical generation activation into one working table: generation rows
are immutable checkpoints; after NORMAL resumes, ordinary postings change the
working table rather than editing the checkpoint. Do not describe an old generation
row as the continuously current balance. Retain before/candidate generations and
drift report after activation or failure.

Existing account versions advance once on successful activation, never reset to the
number of journal lines. Newly restored missing projection rows start at version 1;
the **projection epoch changes for the whole workspace**. This is separate from
R1's schema epoch: migrations and projection activation are different events. Future
optimistic tokens/approvals must bind `(projection_epoch, account_version)`, so a
recreated row cannot revive an old token. Version/epoch exhaustion blocks activation.
An injected failure or lost connection must not publish a partial activation; resolve
ambiguous outcomes by the same maintenance identity and committed metadata.

Activation commits with mode still FROZEN. A separate explicit resume obtains the
same exclusive barrier, checks the freeze identity and fresh validation of the
current projection/source, records completion and moves FROZEN→NORMAL. A rejected
or failed rebuild does not silently unfreeze. Resume after a no-op investigation
also needs clean fresh verification. Concurrent resume, re-freeze and stale candidate
activation must be tested; old tokens cannot control a new freeze session.

## 5. Full internal reversal (decisions 4 and 5)

### 5.1 Input, authority and outcomes

Only an ACCEPTED PURCHASE with one complete immutable purchase journal can be
reversed. An OPENING, rejected purchase, reversal, uncommitted/not-visible purchase,
foreign workspace object or corrupt original is not an eligible original. Do not
follow chains of reversals or accept caller-selected accounts/amounts/currency.
Verify original canonical instruction and exact two purchase entries agree before
using the original amount and account mapping.

Proposed public Python input is a typed full-reversal command: new operation UUID,
original purchase UUID and reason; workspace comes from trusted scope. Reason is a
nonempty, valid UTF-8 string of at most 256 bytes with no NUL, preserved as submitted
and included in canonical comparison. Canonical reversal bytes have their own v1
prefix and fixed field order; purchase v1 bytes remain unchanged. Request route is
`reversal:v1`, request key scope remains workspace/client/route/key. Business IDs
remain unique across kinds within a workspace. Changing original/reason with the
same identity conflicts, just as changing purchase amount does.

Recommended authority: the principal actor owns the **original merchant account**;
reversal credits only the original customer's account. Validate workspace/client
scope and the stored original's immutable owner before disclosing existence, result
or conflict. New reversal needs both accounts enabled and their correct PLN liability
classes; retained-result replay checks ownership but does not re-evaluate later
balance or enablement changes. The caller remains the trusted authentication boundary;
no token adapter, merchant UI or R5 operator approval is implied.

| Submission | Proposed outcome |
|---|---|
| New eligible reversal with enough merchant available balance | Persist 201 accepted full reversal and exactly one effect relation/journal. |
| Eligible original, insufficient available balance | Persist 422 `INSUFFICIENT_AVAILABLE`, no financial effect/success relation. |
| Eligible original, cumulative/version bound exhausted | Persist 422 `LIMIT_EXCEEDED`, no financial effect/success relation. |
| New attempt after a successful reversal of that purchase | Persist 422 `ALREADY_REVERSED`; check this before availability. |
| Identical retained success/rejection under same key or new key/same business ID | Original persisted status/body, no new effect. |
| Changed request bytes or kind under existing identity | Rollback provisional claims, 409 named identity conflict where authorized. |
| Unknown/ineligible original or wrong principal/scope | Generic non-disclosing error with no retained claim. |
| Structurally inconsistent canonical instruction/journal/result | Internal invariant error and rollback; never a fabricated business rejection. |

Use immutable 201 result fields: new operation ID, original purchase ID, reversal
journal ID, original amount string/currency, effect `purchase_reversed`, version 1.
Rejected results use the stable R1 error envelope and once-generated diagnostic ID.
Success response contains no mutable current balance. Exact field names become
frozen fixtures before implementation. Identity 409 errors remain unretained, distinct
from retained business 422. No new stored409 state is needed under the recommendation.

### 5.2 Uniqueness and atomic effects

Add REVERSAL to the explicit operation/journal kind contracts. Failed attempts may
carry a non-unique original reference on operation; purchase/opening have no original.
Never put whole-table uniqueness on that original reference.

The separate `purchase_reversal_effect` relation has composite primary key
`(workspace_id, original_operation_id)` and scoped uniqueness for reversal operation
ID, plus composite foreign keys to both operations. Insert a row **only on success**,
in the same transaction as reversal journal, balance deltas and both stored results.
No conflict-swallowing clause (including `ON CONFLICT DO NOTHING`) or conversion
of an unexpected success-relation unique
violation into replay: it is a safeguard failure, so rollback and surface the error.

Deferred final-state checks must bind the success relation to an accepted REVERSAL
and eligible accepted PURCHASE with matching original reference and financial journal;
an accepted REVERSAL needs exactly one success relation, a rejected one has none.
Document precisely which checks are DB-enforced versus Python intent checks. Do not
claim a simple foreign key proves amounts/owner intent. Transition and append-only
protections apply to new relation/history rows as appropriate under actual runtime
credentials, with migration/maintenance roles kept separate.

For original purchase Dr customer 80 / Cr merchant 80, reversal posts a **new** journal
Dr merchant 80 / Cr customer 80. Increase merchant debits and customer credits using
one relative update per account; preserve reserved values and require available ≥ 80.
All original entries, headers and purchase responses stay byte-for-byte unchanged.
The old purchase remains accepted: correction is a separate business operation.

## 6. Reuse and lock graph: no copied admission transaction

### 6.1 Shared orchestration

Generalize R1-PR04 only where reversal needs it. Keep one readable transaction
orchestrator and one bounded 40P01/40001 retry boundary; `submit_purchase` and new
`submit_reversal` supply typed command-specific validation/posting behavior. Do not
copy `_submit_purchase_once` into a second transaction body or add a general plugin
framework. Keep the finite PURCHASE/REVERSAL dispatch explicit and reviewable.

Reuse/generalize `_open_admission` for common settings/barrier/mode plus the correct
kind-specific ownership policy. Both paths claim request key **before** business ID.
Reuse the two replay paths with kind-specific canonical parsing, stored-owner
validation, outcome and journal/relation checks. Old purchase payloads/replays remain
valid. Same-key replay performs no terminal UPDATE; new-key/business replay finalizes
only the new request association. Extract balance/journal/result primitives only
when both concrete paths need them; do not replicate financial posting SQL wholesale.
Keep existing purchase fault/lock tests and add the reversal counterparts.

### 6.2 Acquisition order

One business call handles one workspace, one new operation and at most one original:

| Rank | Purchase | New reversal | Retained replay |
|---|---|---|---|
| 1 | Shared workspace barrier, then mode/auth | Same | Same, even when only returning an existing result. |
| 2 | Scoped request-key claim | Same | Losing claim waits for winner, then a new statement reads committed result. |
| 3 | Own business-operation claim | Own reversal-operation claim | New-key replay locks only the existing own operation as R1 does. |
| 4 | No original operation | Lock original successful PURCHASE `FOR UPDATE`, then check success relation | No new original/balance locks or fresh financial decision. |
| 5 | Balance rows, ascending account UUID | Same, after original lock | None. |
| 6 | Journal/deltas/results | Success relation/new journal/deltas/results in one transaction | Return/associate immutable retained outcome. |

Original eligibility and owner can first be read without row locks; revalidate the
posted successful original under its rank 4 lock. Reject non-PURCHASE original kinds;
never acquire another reversal as an original. If original equals the new business
ID, reject without constructing a self-reference. Keep original/success checks ahead
of balance locks; no path may acquire balances then wait for the original operation.

Why these current paths do not create an application lock-order cycle:

- Concurrent reversals of the same original serialize on that purchase row. After
  the winner commits, READ COMMITTED's next statement sees its effect relation;
  the loser retains `ALREADY_REVERSED`, not another posting.
- A new purchase holds its own new operation and then sorted balances. A reversal
  can reference only an already committed accepted purchase, so it cannot take that
  new uncommitted purchase as its original while it holds balance locks.
- A purchase/business replay may briefly hold the original purchase row, but never
  waits for balances or a reversal row. Existing reversal replay locks only its own
  retained operation and reads immutable original data without new row locks.
- Two different originals can share balances, but both acquire them in the same UUID
  order. Maintenance takes the exclusive workspace barrier before all lower locks,
  waits for writers without holding their operation/balance locks, then acts alone.

This reasoning depends on **all relevant paths** following the order and terminal
immutability. It does not prove arbitrary SQL, future batch paths, uniqueness/FK
waits or administrators cannot deadlock. Preserve bounded whole-transaction retry,
lock/statement timeouts and cancellation cleanup. No unbounded wait or retry is success.
Future multi-operation maintenance needs its own sorted original-ID order and review.
