## 同步接口

- 增加 `PayoutCommand`、`payout:v1` 和 PAYOUT 显式分派。业务请求绑定 workspace、operation、
  merchant account、beneficiary、provider namespace、本金/手续费/币种/协议版本。
  `Principal` 校验商户 owner；受信策略校验 beneficiary 所有权、固定费率和 namespace。
- 只在新业务准入时生成 deadline；保存不可变 provider request 字节/摘要。
  旧请求重放保持原202/正文与 deadline，不随当前策略重新计算；后续认知另表查询。
- 复用 `_submit_once` 的屏障→模式→请求键→业务ID→业务步骤，不能默认走 reversal else。
  `_finish_operation`、存储结果解析、类型/路由及 SQL 状态约束一起支持 PAYOUT/ACCEPTED/202。
- 新表拟为 `payout`、`reservation`、`reservation_event`、`dispatch_intent`、`transport_attempt`；
  每个主体含 workspace 复合引用。202要求同事务一个hold/HELD事件/READY意图，无出金journal；
  422没有hold/意图/金融效果。后续终结再增加终局约束，不能提前留下可随意消费的后门。
- worker 先锁 operation/payout，再锁 intent；原子记录 MAY_HAVE_SENT/UNKNOWN 与有界 next_due_at，
  提交后联网。扫描包括到期 IN_FLIGHT/OBSERVING，不只扫描 READY。
  截止前同 key 同字节重发；截止后 close。旧 attempt 只补自己的传输事实，不覆盖新 claim/终局。

## 迁移、导出与重建

- 新迁移追加在005后，旧迁移字节不改；202只属于PAYOUT，不放宽购买/冲正201/422。
  旧R2数据库已有非零reserved却没有权威hold历史时拒绝升级并报告，不能自动清零或伪造hold。
- v5增加完整 payout/hold/event/intent/attempt 导出；v1–v4白名单和语义保持。
  `_check_operations`、`_check_requests` 与新PAYOUT意图检查器共同支持202。
  独立核对必须从事件折叠reserved，不相信当前state或余额列即可。
- 现场重建分别聚合journal与活动hold后连接，避免多表join乘倍。
  SQL003目前将审计前后reserved锁为0，维护角色也没有reserved写权限；新迁移必须同时扩展。
- `projection_repair.fold_version` 为历史记录保留1，新修复用2。历史修复的after_reserved
  不能与今天已消费之后的hold和比较；按当时记录/来源版本检验审计完整性。
- 新格式结构（含合法hold生命周期）+B通过即可修复包括reserved的投影；只改投影、保存审计、
  epoch递增并事务内独立复验。恢复营业仍要求结构+A，允许合法非零hold。
- PR02报告明确外部终局未覆盖；新增字段若改变已有严格resume报告解析，必须带版本并保留旧分支。
