# LedgerOps R3 决定包：5 项提案，待确认

日期：2026-10-29。代码依据：`73a070c`，R1/R2 已交付；R3 尚未实现。

本轮授权只有文档：本决定包与 [R3 任务契约](tasks/R3.md)。以下都是建议，
没有一项记作用户已批准。流程沿用 R2：先保留提案提交，用户回复后再单独提交采纳修订；
本轮不启动 PR01，不写代码、迁移或 lab，不推送，不改 tracker、Vault 或参考原件。

五项沿用原计划，暂不合并：关单回答“如何证明不会再支付”，手续费回答“谁承担成本”，
模拟器回答“如何独立保存事实”，回调回答“什么证据有权改变账”，hold 回答“何时恢复可用”。
它们影响的契约不同；接受其中一项不自动接受其余四项。

## 共同例子：从购买 80 接到提现 60＋手续费 2

金额都是合成 PLN 的最小单位，100 表示 PLN 1.00。开户客户 100、商户 0、清算资产 100；
客户购买 80 后，客户 20、商户 80、清算资产仍是 100。每项决定都延续这一状态。

| 阶段 | 商户账面 booked | 预留 reserved | 可用 available | 清算资产 |
|---|---:|---:|---:|---:|
| 购买 80 完成 | 80 | 0 | 80 | 100 |
| 提现本金 60、固定手续费 2 获准处理 | 80 | 62 | 18 | 100 |
| 支付商可能已执行，本地尚不知道 | 80 | 62 | 18 | 100 |
| 权威成功证据在本地落账 | 18 | 0 | 18 | 38 |
| 或者权威失败／关单证明未执行 | 80 | 0 | 80 | 100 |

这里的“冻结 62”指资金预留 hold；它与工作区 `FROZEN` 维护模式是两件事。
hold 不产生借贷分录；成功结算才借记商户 62、贷记清算资产 62，同时消费该 hold。

R3 还需要扩展现有契约：购买／冲正目前保存的终态状态码为 201 或 422；提现将新增
**不可变的 202 `accepted_for_processing`**，表示本地已预留并接下任务，不表示支付成功。
未来实施必须一并扩展相应路由、数据库检查、重放校验及独立核对器，不能只改返回数字。
提现后来成功或失败，查询状态可以变化；重试准入请求仍返回原来的 202 和原正文。

## 1. 如何证明未支付：采用持久的关单墓碑

**建议：模拟支付商提供 `close-if-absent`，将“此 key 不会再执行”变成可验证的协议承诺。**

提现业务只使用一个确定的支付商 key，绑定 namespace、workspace 和业务 ID，
同时绑定固定的完整请求。发送 `PUT` 与关单在支付商自己的事务里串行：

- 关单先赢：写入永久 `CLOSED_ABSENT` 墓碑；同 key 的延迟发送只能读回墓碑，不能支付。
- 发送先赢：关单返回已经接受或完成的状态，不删除执行记录，也不取消已接受任务。
- 同 key 换请求内容始终是冲突；不能把另一个请求的墓碑当作当前请求的未执行证明。

**具体例子：** 商户 hold 62 后发送超时。普通查询暂时返回 `NOT_FOUND`，可用仍为 18。
如果关单权威地写入墓碑，本地才释放 62，恢复可用 80。原来的发送即使随后到达也不能扣款。
如果支付商已经成功，关单必须返回该成功，本地仍应消费 hold，最终可用 18。

**备选方案：** 不提供关单权威；查询不到时一直保留 UNKNOWN，等待其他能够证明终局的证据。
这更接近部分真实支付商的能力，但一些任务可能永远无法自动释放。

**代价：** 必须在独立持久存储里保存 key、请求绑定与墓碑，并测试发送／关单的两种竞争顺序。
墓碑保留整个 scenario namespace 的生命周期；重启不能清空它，重置必须换 namespace。
这是模拟器特意提供的强协议，真实支付商未必具有同等能力。

**反例：** “查了十次都没有，所以释放 62。”查询可能落后，原发送也可能仍在途中；
释放之后再成功就会让商户同时花掉这 62。

**一句话解释题：** 为什么 `NOT_FOUND` 不能释放 hold，而正确绑定的关单墓碑可以？

## 2. 手续费由谁承担：商户承担固定报价，总额一起预留

**建议：本金 60、手续费 2、总额 62 固定写进规范化业务请求，由商户承担。**

报价来自本地合成支付协议的明确版本，不是根据支付结果临时重算，也不是任意客户端
填写一个费用就可信。准入需检查该版本的报价和 `principal + fee = gross`，并检查金额上限。
不声称实现真实费率服务；平台也不把这 2 记成自己的手续费收入。

**具体例子：** 商户 80 申请提现 60，固定费用 2。准入预留 62，可用变 18；
成功后商户账面变 18，清算资产 100→38。失败或权威关单则不记出金分录，释放后商户仍为 80。
支付商独立记录收款本金 60 和费用 2，不能只记录一个无法拆解的 62。

**备选方案：** 平台承担费用：只减少商户负债 60，另借记平台费用 2，再贷记清算资产 62。
这需要额外账户、资金来源与预留规则，现有三类账户不能假装已经支持它。
另一方案是成功时再决定费用，但会引入原预留不足以及旧请求含义变化。

**代价：** 请求、hold、支付商证据和核对器都要保存并核对本金／费用／总额／协议版本。
费用变动不能修改原业务或原请求键的含义。新报价需要新业务决定；
**旧提现仍然 UNKNOWN 时，不能把换业务 ID 的新提现当作重试**，否则可能两笔都支付。
应先取得旧业务的权威终局；如确实另开独立提现，必须明确它可能产生第二笔出金。

**反例：** 只预留本金 60，剩余可用 20 又被消费；成功时才加扣费用 2，就可能不够结算。
把原请求的费用从 2 改成 3 再重发，也破坏“同一业务结果稳定”的身份契约。

**一句话解释题：** 为什么成功时清算资产减少 62，而平台没有得到手续费收入 2？

## 3. 模拟支付商怎么做：独立进程、独立 SQLite 文件

**建议：支付商运行在独立本地进程，经本地 HTTP 协议通信，使用自己的 SQLite 文件。**

它不读取 LedgerOps 的“实际结果”来制造一致答案，不共享 PostgreSQL 事务，
也不导入生产记账或金额计算来生成预期。支付商在自己的事务里提交固定请求、执行结果和
至多一次的出金 effect；本地收到回复之前，这些事实就可能已经持久化。

**具体例子：** 购买后商户 80，提现 hold 62；支付商提交本金 60／费用 2 后，
杀掉账本 dispatcher。本地仍是 booked 80／reserved 62；支付商文件里的成功必须继续存在。
重启后用同一 key 观测成功，本地才结算成 18，而不是再付一次。

**备选方案：** 第二套 PostgreSQL 实例也能提供独立存储，但启动、清理和依赖更重。
同一个 PostgreSQL 事务里的“模拟支付商表”或纯内存 mock 更简单，却不能证明跨进程、
跨存储的提交差距和重启后的持久身份。

**代价及对原默认的调整：** 原参考包建议 WAL，并要求核查并发 WAL 相关版本修复。
本提案改为 **rollback journal：`journal_mode=DELETE`、`synchronous=FULL`、
`foreign_keys=ON`、有限 busy timeout**；支付／关单仍用 `BEGIN IMMEDIATE` 串行。
本地小规模模拟器接受读写竞争时的等待，减少第一版并发 WAL 的版本适配负担。
这不表示任意 SQLite 版本都安全，也不表示已经检查本机依赖；PR01 必须记录实际链接的
SQLite 版本、实际生效设置和本地文件系统假设，并用真实多连接／进程测试验证。
遇到不满足契约的依赖就明确失败，不能悄悄切换模式后仍引用未跑过的保证。

支付商 HTTP 只服务这个本地合成协议，不增加银行连接或 LedgerOps 公网业务 HTTP 接口。
SQLite 持久化设置不是远端银行可靠性证明，R3 也不做支付商吞吐量模型。

**反例：** mock 返回成功就算恢复通过；它没有自己的提交记录，无法区分“没有回复”和“没有支付”。

**一句话解释题：** 为什么同样能保存数据，支付商仍要与账本分进程、分存储？

## 4. 什么证据有权改账：认证后的终局观测，矛盾停止该提现的自动处理

**建议：回调和主动查询／关单的结果进入同一个观测与判定入口，只有通过完整校验的
终局证据才能消费或释放 hold。** HTTP 200 和本地 transport 成功本身没有这个权力。

本地合成协议使用带 key ID 的 HMAC，签名绑定明确的消息字节。对终局证据校验支付商 issuer、
namespace、workspace、provider key、业务请求摘要、本金／费用／总额、商户／收款方、币种、事件 ID 和序列。
callback、lookup、close 是接收通道元数据；同一逻辑事件换通道不改签名字节。
暂态 NOT_FOUND 只绑定查找上下文，不冒充已经存在、字段完整的执行记录，也不能据它改钱。
HMAC 密钥代表本地测试支付商的权威，不是商户 `Principal`，也不是 R5 的生产认证或审批。
无效消息隔离保存，不能改钱；合法但冲突的证据需保留原文并产生 incident。

**具体例子：** 商户 hold 62 后，合法成功回调使本地账面 80→18、reserved 62→0，
同时写出金分录。重复相同回调不重复入账；先收到成功再收到旧 ACCEPTED，不倒退状态。
但如果收到同 key 的合法 FAILED，即使它序列更旧，也必须保留为终局矛盾，停止该提现自动处理。
已经消费的 hold 不释放，不通过自动冲正把账“修平”。

**备选方案：** 回调只作提示，必须再主动查询确认；实现的入口较少，但增加请求与恢复延迟，
且主动查询仍需同样的身份、金额和终局验证。完全相信未认证回调不在可接受选项内。

**代价：** 要持久保存观测、重复身份、冲突原文与隔离记录，并定义序列推进规则。
同 event ID 换字节不能被唯一键冲突直接吞掉。旧非终局可以不改变资金；
旧终局的矛盾不能仅因序列较小就丢弃。合法延迟事件也不能仅凭时间较旧被当作无效。
矛盾标志保持；R3 不提供自动清除或恢复该提现自动处理的入口，人工审批留到 R5。

**反例：** 回调只校验“签名正确、金额 62”，却没有核对 key 和商户，
就可能拿另一笔提现的真实成功来消费当前 hold。

**一句话解释题：** 为什么重复成功可以忽略资金效果，而旧序列的矛盾终局仍要报 incident？

## 5. hold 何时释放：由证据决定，不因超时到期

**建议：一旦准入建立 hold，R3 不提供用户取消接口；发送可能发生后，只有权威失败或
正确关单墓碑才能释放。** 权威成功只消费 hold，不称为释放；UNKNOWN 可以长期占用 62。

**具体例子：** 商户 80、hold 62、可用 18。连续超时、500、查不到、重试预算用尽，
都保持可用 18；有成功证据后账面 18／预留 0／可用 18，有失败／墓碑后恢复可用 80。
工作区冻结也不能证明外部付款停止，不能成为释放理由。

**备选方案：** 允许第一次派发 claim 之前取消：必须锁住同一 operation／intent，证明没有
`MAY_HAVE_SENT`，与 claim 串行，并保留不可变取消事件。原包允许这种语义，
但本轮建议暂不提供这条额外写入路径；它不是 UNKNOWN 后取消的替代办法。
按 5 分钟或其他期限自动释放可以提高表面可用性，却没有未执行证明，不建议采用。

**代价：** 资金可能长时间不可用，必须显示未知原因、重试次数和待处理证据，
不能把资源重试上限写成业务失败期限。R3 可以报告未决任务，但没有任意强制释放的运维后门。
“最终能恢复”也只针对故障停止后存在可获得权威终局证据、且本地可写的情况。

**反例：** 五分钟后释放 62，商户把 80 全花掉；第六分钟支付商证明原提现已成功。
账本没有凭空多出的 62 可以补账，超时时钟也没有取消那笔外部支付。

**一句话解释题：** 为什么可以停止立即重试，却不能因此恢复这 62 的可用余额？

## 本轮边界与回复方式

R3 证明范围限于上述合成协议、独立存储和明确测试过的故障矩阵，不是任意真实支付商的
终局语义，也不保证任意故障时序、任意调度或跨任意系统的 exactly-once。
本地 HMAC 不代替生产认证；模拟器重启持久性不代替磁盘永久丢失或旧备份恢复。
PR04 的恢复保留本地准入指令；从旧备份丢失指令后重建账本属于 R5，R4 的结算对账也未提前实现。

可以回复“1–5 按建议”，或列出要修改的编号与具体差异。确认只决定下一版合同采用哪些选择；
不宣称个人掌握度已评估。实施范围和启动指令仍需明确，当前提案提交不启动任何 R3 代码。
