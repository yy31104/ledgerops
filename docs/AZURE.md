# Azure (Terraform, not applied)

[`deploy/terraform/azure/`](../deploy/terraform/azure) describes a small Azure
footprint for LedgerOps. It has only been checked offline (`terraform fmt`,
`terraform validate`, `tflint`, `checkov`) and a local Caddy/Gunicorn smoke test.
It has **never been applied**, needs no account to check, and contains no secrets.

| Module | Resources | Notes |
|---|---|---|
| `logging` | Log Analytics workspace | 30-day retention, **1 GB/day ingestion cap** |
| `key_vault` | Key Vault (RBAC, purge protection, default-deny network), placeholder secrets, audit log | Terraform creates placeholders only; real profiles are set out-of-band so DSNs/tokens never enter state |
| `postgres` | PostgreSQL Flexible Server B1ms, `ledgerops` DB, TLS required, connection logging | Admin password is generated by Terraform (it **is** in state) and copied to Key Vault |
| `container_apps` | Environment, `api` app (API + Caddy, 1–3 replicas), `dispatch` app (provider + worker, exactly 1), one managed identity per app | Each identity can read only its own secrets |
| `budget` | Resource-group consumption budget | Emails at 50 % / 90 % actual and 100 % forecast |

## Deploy

1. Build the runtime image from `ops/linux/Dockerfile` (`--target runtime`) and push it to
   a registry you control (for example Azure Container Registry).
2. Use a remote state backend with encryption and restricted access, e.g. an
   `azurerm` backend on a storage account. State contains the PostgreSQL admin password.
3. Plan and apply:

   ```bash
   az login
   ```

   ```bash
   cd deploy/terraform/azure && terraform init
   ```

   ```bash
   terraform plan -var subscription_id=SUBSCRIPTION_ID -var image=REGISTRY/ledgerops:REVISION -var 'budget_contact_emails=["you@example.com"]' -out tfplan
   ```

   ```bash
   terraform apply tfplan
   ```

4. Add your IP to the Key Vault `network_acls.ip_rules` (or use a private endpoint).
   Then write the real launcher profiles. They have the same JSON shape that
   `ops/linux/bootstrap.py` writes, with `host=<postgres_fqdn> sslmode=require`:

   ```bash
   az keyvault secret set --vault-name KV_NAME --name api-profile --file api-profile.json
   ```

   Repeat for `worker-profile`, `provider-profile`, `provider-keys` and `payout-policy`.
   Generate the files on a trusted machine and delete them afterwards.
   The API profile must bind to `127.0.0.1:8080`, trust only `127.0.0.1` / `::1`,
   and allow `localhost` (probes) and the app's ingress FQDN in its host allowlist.
5. Run `bootstrap provision` once against the server. It creates roles and migrations
   and should run as a Container Apps Job or from a trusted host.
6. Leave the defaults alone until recovery checks pass: `LEDGEROPS_RESTORE_MODE=true`,
   `LEDGEROPS_API_WRITES_ENABLED=false`, `LEDGEROPS_DISPATCH_ENABLED=false`. These are the
   same reopening rules as in [`ops/linux/README.md`](../ops/linux/README.md).

Check without an account:

```bash
cd deploy/terraform/azure
terraform init -backend=false
terraform fmt -check -recursive
terraform validate
tflint --recursive
checkov -d . --framework terraform
```

## HTTPS request path

```text
HTTPS client → Container Apps ingress (TLS termination)
             → Caddy :8081 → 127.0.0.1:8080 Gunicorn → LedgerOps
```

Ingress targets **8081**, with `allow_insecure_connections = false`. Containers
in one Container App share a network namespace, so Caddy reaches Gunicorn over
loopback. The application keeps its exact-IP trusted proxy list; no Azure
ingress IP or private address range is added to it.

The digest-pinned Caddy 2.11.7 sidecar gets its configuration from the module's
`Caddyfile`, encoded in a non-secret environment variable and decoded into `/tmp`
at startup. It overwrites `X-Forwarded-Proto` with `https`: the external ingress
has already enforced HTTPS, while the hop from ingress to Caddy uses HTTP.
Caddy preserves the request Host, and Gunicorn accepts the scheme header from
its loopback peer. Host and Origin checks remain in the application.

API probes remain on 8080. The sidecar has a TCP liveness probe on 8081 and an
HTTP readiness probe through to `/health/ready`, so an unavailable proxy cannot
receive ingress traffic. As with the API probe, readiness stays false while the
restore/write gates are closed. The sidecar adds **0.25 vCPU / 0.5 GiB per API
replica**, for a combined 0.75 vCPU / 1.5 GiB.

References: [Container Apps ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview),
[shared container networking](https://learn.microsoft.com/en-us/azure/container-apps/containers#multiple-containers),
[Caddy header handling](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers).

## Local proxy verification

From the repository root, with Caddy 2.11.7 available locally:

```bash
make bootstrap
uv run --locked python deploy/terraform/azure/smoke_proxy.py --caddy /path/to/caddy
```

This starts the real production Gunicorn/Application with a deliberately absent
database and ephemeral loopback ports. It verifies six cases: direct HTTP is
rejected with `HTTPS_REQUIRED`; proxy requests and a valid HTTPS Origin succeed;
an incoming `X-Forwarded-Proto: http` is replaced; invalid Host and Origin still
fail. Responses must have a body, so a proxy's unmatched-host empty response
cannot satisfy the test. It closes only the two processes it creates.

Actual result: `checks_passed: 6`, direct HTTP 400, proxied console 200.
For the break experiment, add `--break-forwarded-proto`. This removes the header
override only from a temporary Caddyfile; the same test fails on the proxied
request with HTTP 400 / `HTTPS_REQUIRED`. The committed configuration is untouched.
This proves the local request boundary, not Azure networking or Key Vault startup.

## Estimated monthly cost

West Europe in USD, rounded, at 730 hours/month. Container Apps rates were read
from the [Azure Retail Prices API](https://prices.azure.com/api/retail/prices)
on 2026-11-05, filtered to `Azure Container Apps`, `westeurope`, `Consumption`:
active vCPU $0.000034/s, idle vCPU $0.000004/s, memory $0.000004/GiB-s.
The CPU/memory rows below are before subscription-wide free grants, request
charges and tax. Other rows retain the earlier rough estimates; check them in
the [Azure pricing calculator](https://azure.microsoft.com/pricing/calculator/).

| Item | Assumption | Low | High |
|---|---|---:|---:|
| PostgreSQL Flexible B1ms | 730 h compute + 32 GiB storage + 7-day backup | 16 | 18 |
| Container Apps `api` + proxy | 0.75 vCPU / 1.5 GiB, 1 replica; all-idle → all-active | 24 | 83 |
| Container Apps `dispatch` | 2 × 0.25 vCPU / 0.5 GiB, all-active (worker polls every 500 ms) | 55 | 55 |
| Log Analytics | 5 GB/month free, then per-GB; capped at 1 GB/day | 0 | 75 |
| Key Vault | < 100k operations | 0 | 1 |
| Budget, managed identities | free | 0 | 0 |
| **Total** | One API replica | **~95** | **~232** |

For example, the API active row is `730 × 3600 × (0.75 × 0.000034 + 1.5 × 0.000004)`.
Each additional fully active API replica adds about $83/month; autoscaling to
three increases that row to about $249. Free grants can reduce bills but are
shared across a subscription. The $60 budget is an alert threshold, not a
spending cap, and is below this always-on footprint's pre-grant estimate.

## Teardown

```bash
cd deploy/terraform/azure && terraform destroy -var subscription_id=SUBSCRIPTION_ID -var image=REGISTRY/ledgerops:REVISION -var 'budget_contact_emails=["you@example.com"]'
```

Key Vault has purge protection, so it stays soft-deleted for 7 days and its name is
reserved for that time. This is deliberate. Afterwards, check that nothing is left:

```bash
az group show --name rg-ledgerops
```

## Known limitations

- The localhost proxy path has been exercised locally, but no Container Apps
  deployment, Azure-managed ingress, Key Vault mount or managed identity was tested.
- **Provider SQLite is ephemeral** (`EmptyDir`). SQLite on Azure Files (SMB) is unsafe
  for locking, so a restart loses provider history. That is acceptable only while
  dispatch stays disabled. This is a simulator and does not reach real money.
- PostgreSQL major version is 17 here; the app is tested on 18.6. Check that
  Flexible Server offers 18 in your region before applying, and run the test suite
  against the version you choose.
- `bootstrap provision` is not wired up as a Container Apps Job.
- TFLint ran the bundled `terraform` ruleset. The optional `azurerm` ruleset is
  commented out in `.tflint.hcl` and was not run.
