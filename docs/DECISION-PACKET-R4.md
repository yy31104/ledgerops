# R4 工程决定记录（直接推进范围内）

用户授权直接完成后续工程。本页记录实现者采用的默认与代价，不把这些选择虚记成用户逐项答题。

1. **明确成员对账。** 商户80，提现60+2及10+2，两个provider key合计74；statement可拆两行，
   但每行必须列成员，合计principal70/fee4/gross74。备选是按相近金额或时间猜配；代价是看起来
   匹配率高但难审计。反例：两个商户都提现60，金额相同不能决定归属。复核要点：先确定谁的哪几笔，才相加。
2. **结算时间单独保存。** 10月29日记账62、30日结算62，可以报告明确跨窗口；收到HTTP通知的时间
   不代替支付时间。备选给旧事件补一个推测执行时间，代价是制造无法证明的历史。反例：网络停一天，
   到30日才收到29日付款通知。复核要点：记账、结算、接收分别描述不同事实。
3. **不可变run与完整发布。** 两个分区只完成一个时，旧完整结果继续可读，新run保持STAGING。
   备选逐行覆盖当前报告，代价是读者可能看到两个版本拼接。反例：新数据修正手续费2→3，只有半数分区更新，
   汇总不属于任何真实版本。复核要点：完成、current指针与epoch必须在同一受保护事务里决定。
4. **完整组并行，不做租约重分配。** 1/2/4进程跑同一输入；某个组占90%工作量时可能不加速。
   备选现在做通用任务租约/重分配，代价是增加代次和过期所有权协议。本期子进程死则整run失败，
   新UUID重跑，迟到旧结果拒绝。反例：把一个结算组拆给两人，各自都以为缺一半成员。
   复核要点：优化不能改变匹配语义，失败尝试也必须记录，不挑快的结果汇报。
