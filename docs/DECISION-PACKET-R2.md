## 1. 独立核对：分别核对“算得上”和“记给谁”

**建议：两种核对都保留，结果分开报告。**

- 核对 A：只读原始账户和分录，独立重算每个账户，比较余额投影；零活动账户也要算。
- 核对 B：用事先冻结的业务指令清单，独立检查购买/冲正的账户、金额、状态和原交易关系。
  清单不能从实际分录或生产记账函数反推。
- 没有独立指令清单时，只能说“账内累计一致、业务意图未核实”，不能说完整正确。

**例子：** 客户原本要给 M1 80，程序把分录和余额都记给了 M2。
A 会通过，B 必须报告 `WRONG_OWNER`。此时禁止借重建把错误掩盖成“已修好”。

**可选方案：** 只做分录与余额核对。实现更少，也能抓漏更新，但不能判断收款人是否正确。

**代价：** 多维护一份小型独立命令模型和冻结清单；模拟数据的预期要先手算。
清单本身也可能错，因此冲突先报证据差异，不自动篡改历史分录。

**反例：** “借贷平衡、余额对得上，所以这笔钱一定记对了。”错；两边可能一起记错人。

**拍板后要能回答：** 为什么重新累计分录，仍然发现不了“分录和余额一起记给 M2”？

## 2. 导出：一个数据库快照，一份有边界的本地 JSON 包

**建议：R2 采用版本化 JSON 导出包，在同一个只读 REPEATABLE READ 事务中读取完整内容。**

导出包含指定 workspace 的账户、业务/请求记录、分录表头/明细、当前余额、成功冲正关系、
重建/冻结身份等。金额保持整数的十进制字符串，UUID/顺序/空值规则固定；不靠时间戳猜范围。
先写临时目录，完整写入并核验后再发布为最终目录，校验失败或进程中断不能被当成完整导出。
数据文件可保存内容摘要以查损坏；这不是另建 SHA-256 **源码**清单，源码版本由 Git 提交标识。

**例子：** 导出读到旧分录，随后购买提交，又读到新余额，会误报漂移。
单一数据库快照避免把两次读取拼成一个实际上从未存在过的状态。
普通核对可在写入时导出；用于重建激活的导出必须在冻结排空后重新生成。

**可选方案：** 只在数据库里查，不生成文件；或者现在就做分片/流式导出和在线追赶。
前者少一套文件协议但难以离线复核；后者适合更大数据，当前需要额外完整性和追赶机制。

**代价：** 占用磁盘；要处理临时文件、原子发布和不完整包；R2 先服务有明确规模上限的
本地合成数据，超过声明上限就失败，不悄悄截断或宣称海量数据能力。

**反例：** “这个文件的哈希没变，所以它覆盖了完整、正确的账本。”错；摘要只验证已给定字节，
完整性还要检查包声明、表头、成员、行数、作用域以及业务清单。

**拍板后要能回答：** 为什么逐张表各查一次，即便每次都成功，也不一定得到一致导出？

## 3. 重建：冻结排空后建候选，验证通过再一次性激活

**建议：先做离线维护重建，保留前后代次；暂不做在线重建。**

先拿工作区排他屏障，等待在途写事务结束并提交 FROZEN；再从新导出计算候选代次。
候选验证通过后，在一个事务里更新现有 `account_balance` 工作表并推进投影 epoch。
这是一种逻辑代次切换，不通过运行时动态表名或多表重命名切换。
保留切换前的余额快照、候选和差异记录；普通业务不负责修复漂移。
激活后仍保持 FROZEN，恢复 NORMAL 是单独的显式维护操作。

**例子：** 分录算出客户 20，余额表却显示 100。先保留这个差异，冻结后重新核对，
生成客户 20 的候选；激活要全成或全败。不能更新一半余额后让业务继续写。
R2 没有完整预留资金生命周期：发现非零 `reserved` 时，允许核对已入账金额，**拒绝激活重建**，
不能从分录猜预留资金，也不能把它清零。

**可选方案：** 直接原地覆盖余额；或者边写边后台重建再切换。
前者缺少候选与失败隔离，后者必须处理重建期间新增写入、追赶及切换一致性。

**代价：** 维护期间该 workspace 暂停购买、冲正和写入型重放关联；多保存候选与旧快照。
没有数据库所有者绕过协议时，冻结保证受控账本入口排空并拒绝新业务写入；维护写入仍单独受控。
**数据库冻结不代表外部付款已经停止。** 已经离开的外部请求，未来仍需渠道证据判断。

**反例：** 用冻结前生成的旧候选覆盖冻结后已完成购买的余额，会把新的扣款覆盖掉。
候选必须绑定当前冻结身份和投影 epoch，激活时还要重新检查。

**拍板后要能回答：** 为什么把 `mode` 改成 FROZEN，还不等于已经等完所有在途写事务？

## 4. 冲正结果：不足就保留拒绝，已有成功就返回稳定的业务拒绝

**建议：只做原购买的全额内部反向记账；业务拒绝统一保存为 422。**

金额/币种/两个账户从原购买的不可变指令与分录核实，不接受调用者另填退款金额或改收款人。
资金不足保存 `422 INSUFFICIENT_AVAILABLE`；同一原购买已经成功冲正后，
换新业务 ID 再试保存 `422 ALREADY_REVERSED`。请求键/业务 ID 改内容仍沿用 409 身份冲突。
失败记录引用原购买，但只有成功才插入单独的 `purchase_reversal_effect` 关系表。

**必须通过的例子（所有金额是最小单位）：**

1. 开户后客户 100；客户买 80，客户 20、M1 80。
2. 独立合成开户分录给 M1 再增加 60，M1 为 140；测试专用预留 100，可用为 40。
3. 冲正 R-A 需要 80，被拒绝并保留 422；成功关系表仍为空。
4. 再用独立合成开户分录补 40，M1 账面 180、预留 100、可用 80。
5. 重试 R-A 仍返回原 422；新业务 ID R-B 冲正成功：客户 100、M1 账面 100、预留 100。
6. 原购买的分录一字不改；只有 R-B 有成功关系。新业务 ID R-C 再试返回 `ALREADY_REVERSED`。

这些开户与预留操作只是明确标注的测试准备，不代表 R2 实现充值接口、提现或预留生命周期。

**可选方案：** 把 `ALREADY_REVERSED` 保存成 409。语义也能成立，但要扩展目前仅保存
201/422 的终态契约，并在客户端和重放中区分“已处理业务”与“请求身份被改写”。
部分退款和强制透支回收不在 R2 可选范围。

**代价：** 拒绝结果占存储；“补款后再做一次决定”要换业务 ID；冲正会增加借/贷累计，
而不是删除原分录、把累计值减回去。

**反例：** 给所有冲正尝试的 `original_operation_id` 加唯一约束，会让 R-A 的拒绝
永久占住位置，R-B 即使有钱也不能成功。这种约束明确禁止。

**拍板后要能回答：** 为什么失败冲正可以有多条，而成功关系只能有一条？

## 5. 谁能冲正：建议由原商户主体发起，严格校验原交易归属

**建议：本地模拟中，原购买的商户主体才能发起全额冲正。**

受信 Principal 的 workspace/client/actor 来自调用边界。冲正时核实 actor 是原商户账户的
不可变 owner；退款只能回到原购买的客户账户。知道购买 UUID 不构成权限。
购买仍按客户 owner 授权；冲正按原商户 owner 授权，两个业务共享事务和重放框架、保留各自规则。
历史重放也先检查已保存业务的归属；不能换一个自己拥有的账户来探查别人的结果。

**例子：** 客户 C 向 M1 买了 80。M1 的主体可以发起回退到 C；M2 以及只知道原购买 ID
的其他主体都得到不泄露对象的拒绝。C 不能仅凭购买 ID 自动扣 M1 的账。

**可选方案：** 允许原客户直接申请并执行；这相当于本地模型承诺客户有单方面退款权，
必须接受这个业务含义。另一个方案是专用维护操作员发起，但角色权限和操作审计会更复杂，
不能直接把未来 R5 审批能力算作已存在。

**代价：** 要补商户 Principal 的授权样例和跨主体重放测试；未来真实退款流程仍需要
独立的认证和退款政策，当前没有 HTTP、渠道认证或商户后台。

**反例：** “购买存在、金额正确，所以谁传这个 UUID 都能冲正。”这会把对象身份当成权限。

**拍板后要能回答：** 为什么冲正既要检查 workspace，又要核对原商户的 owner？
